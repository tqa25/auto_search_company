## 1. 경영진 요약

V1은 현재 작동 중이지만, 검색, URL 확인, 스크랩, AI 호출 및 데이터 저장 단계가 서로 밀접하게 의존적입니다.

`Pipeline`은 회사 정보 읽기부터 최종 연락처 저장까지의 전체 처리 체인입니다.

`Query`는 앱이 Firecrawl Search를 통해 Google에 보내는 검색어입니다.

`Scrape`은 앱이 계속 처리할 수 있도록 URL 콘텐츠를 다운로드하여 텍스트로 변환하는 것입니다.

`API`는 앱이 Firecrawl과 같은 외부 서비스에 요청을 보내는 포트입니다.

단계에 오류가 발생하거나 시스템이 중단될 경우, 앱은 이미 완료된 부분을 다시 실행하거나, 중복 데이터를 저장하거나, 백그라운드에서 worker를 계속 실행할 수 있습니다.

`Worker`는 작업을 수신하고 처리하는 프로세스입니다. 간단히 말해, 하나의 회사 또는 URL을 처리하는 앱의 독립적인 실행 세션으로 이해할 수 있습니다.

V2는 프로세스를 `module` — 즉, 작은 기능 블록으로 분할할 것이며, 각 블록은 명확한 작업을 수행하며 자체 입력 및 출력을 가집니다.

예를 들어, 쿼리 생성 블록은 검색어만 생성합니다. 이 블록은 Firecrawl을 직접 호출하지 않고, URL을 직접 평가하지 않으며, 데이터베이스에 연락처를 직접 기록하지 않습니다.

각 작은 작업은 `work unit` — 즉, 개별적으로 실행, 중단 및 재시도할 수 있는 작업 단위가 될 것입니다.

예시:

- "회사 A의 2번 쿼리 검색"은 하나의 work unit입니다.
- "URL X에 대한 블랙리스트 확인"은 또 다른 work unit입니다.
- "URL X 스크랩"은 또 다른 work unit입니다.

각 work unit 후에 앱은 `checkpoint` — 즉, 어떤 작업이 완료되었고 어떤 작업이 미완료 상태인지 나타내는 마일스톤을 저장합니다.

시스템이 20개 URL 중 13개를 처리한 후 중단되면, 다음 실행 시에는 나머지 7개 URL만 계속 처리합니다.

### V2가 제공해야 할 결과

| 경영진 요구사항 | 예상 결과 |
|---|---|
| 비용 절감 | 기존 결과가 유효한 경우 다시 검색, 스크랩 또는 AI 호출을 하지 않음. |
| 잘못된 데이터 감소 | 쿼리는 항상 시/도와 연결됨; AI는 회사와 관련된 부분만 읽음. |
| 검사 용이성 | 각 단계는 자체 입력, 출력 및 결정 이유를 가짐. |
| 재개 용이성 | 중단된 지점에서부터 계속 진행하며, 전체 회사를 다시 실행하지 않음. |
| 더 빠른 실행 | 여러 worker가 병렬로 실행되지만 동일한 작업을 중복해서 가져가지 않음. |
| 실제 중단 | 대시보드는 새로운 작업 발행처와 실행 중인 worker를 모두 중단시키며, 단순히 표시 상태만 변경하지 않음. |
| 비즈니스 로직 변경 용이성 | 도메인, 소스 순서, 점수 및 쿼리 공식은 구성 파일에 있음. |

### V2 구축 방식: V1 복사본을 점진적으로 수정

V2는 처음부터 다시 작성되지 **않아야** 합니다.

이유: V1에는 V2에 필요한 많은 기능이 이미 존재하며, 해당 기능들은 올바르게 작동하고 있습니다.

| V2에 필요한 기능 | V1에 이미 있는 기능 |
|---|---|
| 두 worker가 동일한 작업을 경쟁하지 않음 | `BEGIN IMMEDIATE`를 사용한 작업 클레임 |
| worker 사망 감지 | `heartbeat`, 15분 임계값 |
| 비용을 다시 지불하지 않고 계속 실행 | `ai_extract_pending` 체크포인트 |
| 실행 중 안전하게 중단 | 안전 경계에서의 중단 확인 |
| 일시적 오류 / 무시 / 완전 중단 오류 분류 | `src/errors.py` |
| URL 점수표, 도메인 블랙리스트, 도메인별 중복 제거 | `src/filter_module.py` |
| 회사 활동 상태 확인 | `src/business_status.py` |
| 누락된 세금 코드 및 베트남어 회사명 보충 | `src/gemini_quick_search.py` |
| 비용이 많이 드는 API 호출 없이 전체 흐름 다시 실행 | Replay mode |

V2의 실제 작업은 작업 단위를 "하나의 회사" 수준에서 "하나의 작은 작업" 수준으로 **세분화**하고, 코드를 여러 작은 모듈로 **분리**하는 것입니다. 이것은 재구축이 아니라 수정 작업입니다.

구현 방식:

```text
V1을 V2용 root로 복사
제외: output/, re_extract_tool/, venv/, graphify/, graphify-out/, index/
별도로 복사: data/company_data.db
V2 root에 venv 다시 생성 (기존 venv 복사 안 함)
```

복사 후 V1은 그대로 유지되며 더 이상 수정되지 않습니다. V1은 결과 비교 및 V2가 요구사항을 충족하지 못할 경우의 롤백 방안으로 사용됩니다.

## 2. V2가 수정해야 할 V1의 네 가지 문제

이 섹션에는 V2 결정만 기록됩니다. V1 코드, 데이터베이스 및 데이터 제한에 대한 증거는 `docs/v1-operational-audit.md`에 있습니다.

| V1 문제 | V2의 필수 결정 |
|---|---|
| 쿼리에 시/도가 누락되어 있고 AI가 뉴스 페이지 바닥글에서 연락처를 가져올 수 있음 | 이름으로 쿼리할 때는 시/도가 포함되어야 함. AI는 회사 식별 증거 근처의 부분만 읽음. |
| 재시도가 조기에 중단되거나 일시적 오류가 빈 결과로 변경됨 | 공통 retry executor 사용. HTTP 5xx 및 timeout은 조정 계층까지 올바른 오류 유형을 유지해야 함. |
| 캐시 히트 시에도 검색 결과가 추가로 저장됨 | 캐시 히트 시 다시 저장하지 않음. 중복 데이터 정리 후 고유 키 `(company_id, search_query, url)` 추가. |
| 모든 페이지가 3초 고정 대기 | `wait_for_ms=0` 기본값. 특정 도메인만 자체 selector 또는 대기 시간을 가짐. |

이전 계획에서는 여러 회사에서 공유하는 검색 결과 세트를 제안했었습니다. 해당 제안은 쿼리가 일반적으로 회사 이름을 포함하고 거의 공유되지 않기 때문에 폐기되었습니다.

V2는 회사별로 검색 결과를 유지합니다. 이 방식은 해당 회사의 개별 검토, 상태 및 결정 이유를 보존합니다.

캐시 마이그레이션 세부 정보는 10절에 있습니다. 재시도 규칙은 11절에 있습니다. 스크랩 구성은 12절에 있습니다. 필수 회귀 테스트는 17절에 있습니다.

## 3. V2 운영 원칙

### 3.1 비용이 드는 각 단계 전에 비용 확인

V2는 URL이 있다고 해서 자동으로 스크랩하지 않습니다.

스크랩 전에 앱은 다음을 순서대로 확인합니다:

회사가 아직 활동 중인지 아니면 해산되었는지. 만약 해산되었다면 어떤 URL도 스크랩하지 않는다.
2. URL에 캐시된 결과가 아직 최신인지 아닌지.
3. 동일한 도메인 내에서는 **가장 높은 점수의 URL 하나만** 유지한다. 해당 도메인의 나머지 URL은 열어서는 안 된다.
4. URL이 충분한 점수와 충분한 증거를 가지고 있는지 아닌지.
5. URL 또는 페이지의 세금 코드가 목표 세금 코드와 충돌하는지 아닌지.
6. 도메인이 저렴한 GET 요청으로 HTML 검사를 허용하는지 아닌지.
7. HTML 또는 검색 결과 요약 정보에 블랙리스트 번호가 포함되어 있는지 아닌지.
8. 현재 티어에서 유효한 번호를 찾았고 중단해야 하는지 아닌지.

검사 1과 3은 가장 큰 비용 절감 단계이다. V1에는 이미 두 가지 모두 있었고 V2는 이를 유지해야 한다.

검사 3의 효과 예시:

```text
쿼리는 yellowpages.vn에 속하는 10개의 URL을 반환합니다.
도메인 중복 제거 없음: 10개의 URL 열기 → 10 크레딧 소모 → 1페이지와 동일한 정보
도메인 중복 제거 있음:    1개의 URL 열기  → 1 크레딧 소모  → 동등한 정보
```

`Tier`는 동일한 우선순위 수준을 가진 소스 그룹이다.

예시:

- Tier 1: Business Directory.
- Tier 2: Job Portal.
- Tier 3: Facebook.

티어의 순서와 개수는 사용자가 구성한다. 앱은 위 세 그룹만을 코드에 고정적으로 작성하지 않는다.

### 3.2 모든 중요한 결정은 Source Policy에 있다

`Source Policy`는 앱이 어떤 도메인을 우선시해야 하는지, 몇 점을 추가해야 하는지, 언제 스크랩하고 언제 중단해야 하는지를 알려주는 규칙 파일이다.

실행할 때마다 버전이 포함된 정책 스냅샷을 유지한다.

`Snapshot`은 시작 시점의 입력 및 구성 스냅샷이다. 이를 통해 앱은 어떤 규칙에 따라 결과가 생성되었는지 설명할 수 있다.

정책이 변경되더라도 이전 결과는 삭제되지 않는다. 앱은 해당 결과를 `stale`로 표시한다 — 이는 이전 규칙에 따라 생성된 결과이며 다시 계산해야 할 수도 있다.

### 3.3 쿼리에 사용된 필드는 자체 확인을 위해 다시 사용해서는 안 된다

`Field`는 회사명, 세금 코드, 주/시 또는 법정 대리인과 같은 데이터 필드이다.

쿼리 사용 예시:

```text
베트남어 이름 + 성/시 + 연락처 키워드
```

베트남어 회사명과 주/시는 Google이 올바른 방향을 찾도록 돕는다.

이 규칙은 앱이 검색에 사용한 단어를 URL이 반복한다는 이유만으로 "올바른 URL"이라고 자체적으로 결론 내리는 상황을 방지한다.

#### 쿼리에 사용된 필드는 여전히 점수에 반영되지만, 더 적은 점수를 받는다

쿼리에 사용된 필드는 **완전히 제외되지 않는다**. 이는 여전히 유용한 정보이지만, 독립적인 증거로 간주되지는 않는다.

이유: Google은 항상 검색한 정확한 구문이 포함된 페이지를 반환하지는 않는다. 회사명이 실제로 페이지에 있는지 확인하는 것은 여전히 가치가 있다.

V2는 증거를 세 가지 유형으로 나눈다:

| 증거 유형 | 점수 | URL을 `accepted`로 자체 전환 가능 여부 |
|---|---|---|
| 쿼리에 **아직** 사용되지 않은 필드 (예: 세금 코드, 법정 대리인) | 전체 점수 | 가능 |
| 쿼리에 **이미** 사용된 필드 (예: 이름, 주/시) | 점수 감소, 기본값은 전체 점수의 25% | 불가능 |
| 식별 증거 없음 | 0 | 불가능 |

URL이 `accepted`가 되기 위한 조건:

```text
총점 >= 정책 임계값 (기본값 35)
AND 쿼리에서 사용되지 않은 증거가 하나 이상 있는 경우
```

URL이 충분한 점수를 얻었지만 쿼리에 사용된 증거만 **있는 경우**, URL은 `rejected`가 아닌 `deferred` 그룹으로 분류된다.

예시:

```text
사용된 쿼리: vietnamese_name + province

URL A: 페이지에 회사 이름이 있고, 올바른 세금 코드가 있음
       → 이름: 25% 점수 (쿼리에서 이미 사용됨)
       → 세금 코드: 전체 점수 (쿼리에서 아직 사용되지 않음)
       → 독립적인 증거가 있음 → 승인됨

URL B: 페이지에 회사 이름과 시/도만 있음
       → 둘 다 쿼리에서 이미 사용됨 → 25% 점수만 받음
       → 독립적인 증거가 없음 → 보류됨, 사용자 검토 대기 중
```

25% 비율은 정책에 설정되어 있다. 사용자는 더 엄격하게 하려면 0%로 변경하거나, 너무 많은 올바른 URL이 `deferred`로 밀려난다고 판단되면 50%로 변경할 수 있다.

### 3.4 대체 결정이 없는 경우 V1 규칙은 유지된다

기본 규칙은 여전히 다음과 같다:

```text
10개의 고품질 URL을 충분히 확보할 때까지 쿼리를 계속합니다.
고품질 URL은 점수가 35점 이상이어야 합니다.
10개의 URL이 충분히 확보되면 새 쿼리 생성을 중단하고 스크랩 단계를 시작합니다.
```

35점과 10개라는 수량은 정책에 설정되어 있다. 사용자는 코드 수정 없이 나중에 변경할 수 있다.

내보내기 파일은 여전히 각 Search Result URL을 역추적할 수 있는 기능을 유지한다.

URL에서 직접 가져온 정보는 회사 수준에서 집계된 정보와 구별되어야 한다.

business status, replay 및 force refresh에 대한 V1 규칙은 새로운 비즈니스 요구사항과 명확한 대체 테스트가 있을 때만 변경된다.

### 3.5 쿼리 생성 전 식별 데이터 보충

V1의 첫 번째 단계는 `Gemini Quick Search`이다 — Google Search Grounding을 사용하여 회사의 식별 정보를 조회한다.

이 단계는 누락된 필드인 세금 코드, 베트남어 회사명, 주소를 채운다.

V2는 **이 단계를 첫 번째 단계로 그대로 유지한다**.

필수적인 이유: 5.4항의 규칙은 "주/시가 없으면 세금 코드 쿼리로 전환한다"고 명시한다. Quick Search 단계를 생략하면 세금 코드가 채워지지 않아 해당 예비 규칙이 무의미해진다.

예시:

```text
입력 라인: CÔNG TY TNHH MINH AN (주소 없음, 세금 코드 없음)

빠른 검색 사용 시: Gemini가 세금 코드 3701234567과 빈즈엉 성을 반환합니다.
                  → 앱이 올바른 쿼리를 생성합니다.

빠른 검색 미사용 시: 성/시 없음, 세금 코드 없음
                  → 회사가 수동 확인이 필요한 목록에 추가됩니다.
```

현재 데이터베이스에서 8,701개 회사 중 1,252개 회사에 주소가 없다. 이 그룹이 바로 이 단계가 가장 필요한 그룹이다.

Quick Search는 **회사 수준**에서 연락처를 생성한다. 회사 수준 연락처는 특정 URL에서 가져온 연락처와 구별되어야 한다.

### 3.6 스크랩 전 회사 활동 상태 확인

V1에는 `business status gate`가 있었다 — 이는 법적 출처 페이지를 읽어 활동 상태를 가져오는 단계이다.

일시 중단, 해산, 세금 코드 폐쇄 또는 파산 대기 중인 회사는 이유가 기록된 채 즉시 종료된다.

"등록된 주소에서 활동하지 않음"은 중단 조건이 **아니다**.

V2는 이 단계를 그대로 유지한다. 이는 전체 시스템에서 가장 큰 비용 절감 단계이다.

2024년에 해산된 회사 예시:

```text
게이트 있음: 법률 페이지 1개 읽기 → "해산됨" 발견 → 종료 → 약 1 크레딧 소모
게이트 없음: URL 10개 평가 → URL 10개 스크랩 → AI 10번 호출 → 아무것도 찾지 못함
```

이 단계는 먼저 페이지를 스크랩해야 하므로, 3.1항의 "모든 비용이 드는 단계 전에 비용을 확인"하는 규칙에 대한 의도적인 예외이다.

### 3.7 Tax code는 앱이 확실할 때만 URL을 차단해야 합니다.

Tax code는 증거이면서 동시에 거부권입니다.

비즈니스 규칙: 두 Tax code 모두 확실히 알고 두 값이 다르다면 URL은 즉시 제외됩니다.

실제 문제: 웹 페이지의 10자리 숫자열은 Tax code, 전화번호 또는 신분증 번호일 수 있습니다.

#### 베트남 Tax code는 자체적으로 검증 가능합니다.

Tax code의 마지막 자릿수는 앞의 아홉 자리 숫자로부터 계산됩니다. 이것은 무작위 숫자가 아닙니다.

계산 방법:

```text
세금 코드 0100112437

처음 9자리 숫자:  0    1    0    0    1    1    2    4    3
가중치:  31   29   23   19   17   13   7    5    3
곱셈 및 덧셈: 0 + 29 + 0 + 0 + 17 + 13 + 14 + 20 + 9  = 102

102를 11로 나누면  → 나머지 3
10 - 3 = 7   → 마지막 숫자는 7이어야 합니다   → 맞음
```

전화번호는 이 규칙이 없으므로 우연의 일치로만 통과됩니다.

현재 데이터베이스 검증 결과:

| 실제 데이터 | 결과 |
|---|---|
| 7,448개 회사 Tax code | 99.9%가 검증을 통과 |
| 5,687개 10자리 전화번호 | 오직 9.9%만 통과 |

단 하나의 계산으로 약 90%의 오인식 사례를 제거할 수 있으며, 이전에 접하지 않은 웹사이트를 포함한 모든 웹사이트에서 적용됩니다.

#### 신뢰도 척도

| 단계 | 검증 | 효과 |
|---|---|---|
| 1 | 정확히 10자리 또는 `...-001` 형태의 13자리 | 형태 필터링 |
| 2 | 마지막 자릿수 검증 통과 | 전화번호의 90% 제거 |
| 3 | 숫자 바로 앞에 `MST`, `Mã số thuế`, `Mã số doanh nghiệp`, `Tax code` 문자가 있는 경우 | 매우 강력한 증거 |
| 4 | 숫자 바로 앞에 `Điện thoại`, `Hotline`, `Tel`, `Zalo` 문자가 있는 경우 | 이것은 전화번호임 — 제외 |
| 5 | Tax code가 URL 경로 자체에 포함된 경우 | 가장 강력함, V1에서 masothue에 사용됨 |

#### 처음 접하는 낯선 페이지: 두 개가 아닌 세 가지 결과를 사용

이것은 이 항목의 가장 중요한 규칙입니다.

| 결과 | 의미 | 앱 동작 |
|---|---|---|
| `match` | 확실히 Tax code이며 목표와 일치 | 점수 추가 |
| `mismatch` | 확실히 Tax code이며 목표와 다름 | **URL 제외** |
| `unknown` | Tax code인지 여부를 확인할 수 없음 | **아무것도 하지 않음**, 다른 증거로 URL 평가 |

`unknown`은 절대로 URL을 제외해서는 안 됩니다.

두 가지 결과만 사용했을 때의 재앙적인 예시:

```text
목표 세금 코드: 3701234567
알 수 없는 페이지에 포함된 문자열: 0912345678

두 가지 결과: 앱이 그것을 세금 코드로 추측함 → 목표와 다름 → URL 제외
             → 올바른 페이지 하나를 놓침, 명확한 이유 없음

세 가지 결과: 마지막 숫자 검사 실패
             앞에 MST 문자가 없음
             09로 시작하는 번호는 휴대폰 번호임
             → 알 수 없음 → URL은 여전히 도메인, 이름 및 주소로 검토됨
```

두 가지 방향은 서로 다른 두 가지 엄격한 수준을 사용합니다.

- **점수를 추가**하기 위해서는: 1단계와 2단계를 충족하는 것으로 충분합니다. 만약 틀리더라도 좋은 URL 하나만 잃게 됩니다. 피해는 작습니다.
- **URL을 제외**하기 위해서는: 2단계 **및** 3단계를 충족하거나 5단계를 충족해야 합니다. URL을 제외하는 것은 파괴적인 행동이며 사용자에게 흔적을 남기지 않으므로, 추측에 따라 수행되어서는 안 됩니다.

#### Tax code 거부권이 모든 URL을 제외할 때의 안전 브레이크

심지어 `confirmed`된 Tax code도 사용자가 잘못 입력했거나 앱이 이전에 잘못 승격시켰기 때문에 틀릴 수 있습니다.

따라서, 만약 최소한 하나의 `accepted`된 URL이 있거나 **Tax code 검증 전에** 충분한 증거 임계값을 충족했고, Tax code 거부권이 해당 모든 URL이 제외된 유일한 이유라면, 앱은 '찾을 수 없음'이라는 결과로 조용히 종료되어서는 안 됩니다.

앱은 다음을 수행해야 합니다:

```text
해당 URL을 거부 상태로 확정하지 마십시오.
held_for_review 상태를 유지하십시오.
회사 자동 처리를 중지하십시오.
reason = tax_code_veto_rejects_all 로 기록하십시오.
회사를 Deferred Review로 이동시키십시오.
```

검토 화면은 목표 Tax code 및 그 출처, 경쟁 Tax code, 영향받은 URL, 각 페이지의 이름/주소, 그리고 목표 Tax code가 `confirmed`로 승격된 페이지들을 표시해야 합니다.

이 규칙은 최종 결과가 0개의 URL이라고 해서 **실행되지 않습니다**. 만약 URL들이 이미 이름이 틀리거나, 주(province)가 틀리거나, 거부권 행사 전에 식별 증거가 없었기 때문에 점수가 부족했다면, 0개의 URL은 정상적인 결과입니다.

예시:

```text
사용자 잘못 입력: 3701234568
8개 URL은 이름과 주소가 올바르지만, 모두 다음과 같이 기록됨: 3701234567

제어 기능 없음: 8개 URL이 제외됨 → 앱에서 연락처를 찾을 수 없다고 알림
제어 기능 있음:       8개 URL held_for_review
                company reason = tax_code_veto_rejects_all
                사용자는 세금 코드 입력이 잘못되었을 수 있음을 즉시 알 수 있음
```

#### 앱은 낯선 페이지를 점진적으로 학습합니다.

`unknown`을 만날 때마다 앱은 도메인, 발견된 숫자열, 그리고 식별할 수 없는 이유를 기록합니다.

사용자는 이 목록을 정기적으로 검토합니다. 웹사이트가 안정적인 형식을 가지고 있다고 확인되면, 해당 도메인은 정책에 별도의 규칙으로 추가됩니다.

이 덕분에 알려진 도메인들은 점점 더 엄격해지고, 낯선 도메인들은 기본적으로 안전하게 유지됩니다.

### 3.8 Quick Search에 의해 보충된 데이터는 미확인으로 표시되어야 합니다.

이것은 Quick Search 단계의 가장 어려운 문제입니다.

앱은 Quick Search를 사용하여 누락된 필드를 채웁니다. 그러나 Quick Search가 올바른 회사인지 확인하려면 바로 그 필드들이 필요합니다. 이것은 완전히 깨뜨릴 수 없는 순환입니다.

따라서 V2는 Quick Search가 옳다는 것을 증명하려고 시도하지 않습니다. V2는 **신뢰 수준을 표시**하고 미확인 데이터의 **권한을 제한**합니다.

#### 각 필드는 출처와 신뢰 수준을 포함합니다.

| 출처 | 의미 | 신뢰 수준 |
|---|---|---|
| `user_input` | 사용자가 파일에 입력 | `confirmed` |
| `quick_search` | Gemini가 검색 | `unconfirmed` |
| `scraped` | 스크랩된 페이지에서 가져옴 | 교차 확인이 있을 때까지 `unconfirmed` |

#### 미확인 필드의 권한

이것은 이 항목의 가장 중요한 규칙입니다.

| 작업 | `confirmed` 필드 | `unconfirmed` 필드 |
|---|---|---|
| 쿼리 생성에 사용 | 허용 | 허용 |
| URL에 점수 추가 | 전체 점수 | 점수 절반 감소 |
| **URL 제외 (거부권)** | **허용** | **절대 불가** |

거부권 규칙의 이유: 만약 Gemini가 잘못된 Tax code를 반환하고 앱이 그 Tax code를 사용하여 URL을 제외한다면, **모든 올바른 URL이 제외될 것**이며 사용자는 원인을 알 수 없습니다. Gemini의 한 번의 잘못된 추측이 해당 회사 전체를 망가뜨릴 것입니다.

이것은 또한 3.7 항목과의 연결점입니다: `mismatch`는 목표 Tax code가 `confirmed`일 때만 URL을 제외할 수 있습니다.

#### 가져오기 시 점수 시스템 자체를 사용하여 Quick Search 결과 검증

V1은 임포트 단계에서 회사 매칭 점수 시스템을 이미 가지고 있었습니다. 세금 코드(tax code)가 일치하면 100점을 받습니다. 이름/성/주소/도메인/전화번호는 점수에 기여하며, 세금 코드(tax code)가 다르면 0점을 받습니다. 자동 매칭은 85점 이상이 필요하며, 두 번째로 높은 점수와 15점 차이가 나야 합니다.

V2는 이 시스템을 그대로 재사용하여 Quick Search 결과를 원본 입력 라인과 비교하여 점수를 매깁니다.

```text
사용자 입력: CÔNG TY TNHH MINH AN, Bình Dương
Gemini 반환: CÔNG TY TNHH MINH AN, Bình Dương, MST 3701234567

→ 이름 일치, 성/도 일치 → 높은 점수 → 수락, 미확인으로 표시
```

```text
사용자 입력:  CÔNG TY TNHH MINH AN, Bình Dương
Gemini 반환:     CÔNG TY TNHH MINH AN, Hà Nội, MST 0101234567

→ 지방이 사용자가 제공한 데이터와 모순됨
→ 수락하지 않음, 사유: quick_search_conflict 기록, 원본 입력 유지
```

**앵커 규칙:** 사용자가 제공한 필드는 Quick Search가 덮어쓰거나 모순되어서는 안 됩니다. Quick Search는 빈칸만 채워야 합니다.

#### Gemini가 동일한 이름의 여러 회사를 반환할 때

앱은 Gemini가 참조한 소스 내에서 서로 다른 회사 수를 계산합니다.

```text
만약 소스들이 1개 회사를 가리킨다면 → 수락, 미확인
만약 소스들이 2개 이상의 회사를 가리킨다면 → 수락하지 않음
                                   → 회사를 검토 대기열에 추가
                                   → 이유: identity_ambiguous
```

앱은 동일한 이름의 여러 회사 중 하나를 자동으로 선택하지 않습니다.

#### unconfirmed에서 confirmed로 승격

프로모션은 필드를 `unconfirmed`에서 `confirmed`로 승격시키는 것입니다. 프로모션 후, 새 필드는 URL 유형을 가질 수 있으므로, 프로모션에 사용되는 모든 증거는 출처를 저장할 수 있어야 하며 다음의 모든 조건을 통과해야 합니다.

1.  최소 두 개의 다른 도메인과 두 개의 다른 `source family`에 속하는 두 개 이상의 지원 페이지가 있어야 합니다. **또는** `authoritative_registry` 유형의 페이지 하나.
2.  해당 페이지는 확인 중인 필드를 포함하는 쿼리로 찾아서는 안 됩니다. 세금 코드(tax code)로 찾은 페이지는 해당 세금 코드(tax code)를 확인하는 데 사용되어서는 안 됩니다.
3.  페이지의 회사 이름은 아래 규칙에 따라 대상 회사와 일치해야 합니다.
4.  필드 주변의 두 단락은 거의 동일해서는 안 됩니다. 앱은 문자, 공백, 구두점을 표준화한 다음 토큰을 비교합니다. 정책 임계값 `promotion_evidence_similarity_threshold` (기본값 `0.85`) 이상의 유사성은 하나의 소스로만 간주됩니다.
5.  경쟁 필드가 조건 1-4를 통과하지 않아야 합니다. 두 개의 세금 코드(tax code)가 모두 충분한 증거를 가지고 있다면, `identity_ambiguous`로 중단됩니다.

`source family`는 동일한 네트워크에 속하거나 동일한 소스를 복사했을 가능성이 있는 웹사이트 그룹입니다. 도메인이 다르더라도 동일한 source family에 속하면 하나의 소스로만 간주됩니다.

각 프로모션은 다음을 저장해야 합니다:

```text
필드와 승격된 값
지원 URL, 도메인 및 source_family
query_id와 쿼리 내 사용된 필드 목록
필드 주변의 증거 조각
회사 이름 일치 점수/관계
정책 버전 및 프로모션 시점
```

나중에 더 신뢰할 수 있는 소스가 모순될 경우, 앱은 필드를 `unconfirmed`로 강등시키고, 영향을 받는 결과를 `stale`로 표시하며, 회사를 검토 대상으로 보냅니다.

#### 이름이 90% 유사하다고 해서 자동으로 동일한 회사는 아닙니다

앱은 유사성을 계산하기 전에 대소문자, 공백, 구두점, 베트남어 악센트 부호 및 기업 유형 표기법을 표준화합니다.

`name_similarity >= promotion_name_probable_threshold` (기본값 `0.90`)는 `probable` 결과만 생성하며, 프로모션에 자동으로 충분하지 않습니다. 대상 이름을 모두 포함하지만 구별되는 단어가 추가된 이름은 여전히 다른 회사일 수 있습니다:

```text
명안
명안 발전
명안 그룹
투자 명안
```

`probable` 이름이 프로모션에 사용되려면, 구체적인 주소, 대표자, 공식 도메인 또는 이미 확인된 세금 코드(tax code)와 같은 최소 하나의 강력한 독립 식별 필드가 추가로 있어야 합니다. 동시에 강력한 모순되는 필드가 없어야 합니다. 서로 다른 세금 코드(tax code)는 항상 이름의 유사성 점수보다 우선합니다.

앱은 단순히 참/거짓만 저장하는 대신 `name_similarity`와 `exact`, `legal_form_variant`, `target_contained_with_suffix`, `probable` 또는 `conflict`와 같은 관계를 모두 저장합니다.

#### 입력에 회사 이름만 있는 경우

이것은 최악의 경우이며 명확한 규칙이 필요합니다.

| 상황 | 앱 동작 |
|---|---|
| Quick Search가 **이름 + 성 + 세금 코드(tax code)**를 반환하고, 하나의 회사만 가리킬 때 | 성과 세금 코드(tax code)를 채우고, `unconfirmed`로 표시하며, 일반 쿼리를 실행합니다. |
| Quick Search가 **세금 코드(tax code)는 반환하지만 성은 없을 때** | 세금 코드(tax code)만으로 쿼리를 실행합니다. 이 쿼리는 성/시가 필요하지 않습니다. |
| Quick Search가 **성은 반환하지만 세금 코드(tax code)는 없을 때** | 이름 + 성으로 쿼리를 실행합니다. URL은 독립적인 증거가 있어야 `accepted`됩니다. |
| Quick Search가 **동일한 이름의 여러 회사를 반환할 때** | 회사를 중단하고, `identity_ambiguous`를 기록하며, 검토 대기열에 추가합니다. |
| Quick Search가 **아무것도 반환하지 못할 때** | 회사를 중단하고, `dependency_missing: province, tax_code`를 기록하며, 입력 보충이 필요한 목록에 추가합니다. |

표의 마지막 두 줄은 "이름만 있는 경우 앱은 무엇을 하는가"라는 질문에 대한 답변입니다. 앱은 이름만으로 쿼리를 실행**하지 않습니다**. 앱은 중단하고 사용자에게 알립니다.

사용자가 데이터가 부족하더라도 시도하고 싶다면, 정책을 활성화할 수 있습니다:

```yaml
allow_name_only_query: false      # 기본값은 비활성화
name_only_score_threshold: 60     # 활성화 시 일반 기준 35보다 높은 임계값 사용
name_only_max_queries: 1          # 쿼리는 하나만 허용
```

이 방법은 사용자에게 결정권을 부여하고 활성화 시 피해를 제한합니다.

## 4. 회사 입력 데이터

### 4.1 주요 필드

| 필드 | 필수 | V2 사용 방법 |
|---|---:|---|
| 회사 이름 | 예 | 회사 입력을 식별하고 정책 선택 시 쿼리를 생성합니다. |
| 베트남어 회사명 | 아니요 | 플레이스홀더를 사용하여 쿼리에 사용할 수 있습니다. |
| 세금 코드(Tax code) | 아니요 | 쿼리를 생성하거나 쿼리에 아직 사용되지 않은 경우 증거로 사용합니다. |
| 성/시 | 아니요, 하지만 기본 이름 쿼리에 필요합니다. | 지역별 검색 결과를 좁힙니다. |
| 법정 대리인 | 아니요 | 쿼리를 생성하거나 독립적인 증거로 사용합니다. |
| 블랙리스트 전화번호 | 아니요 | URL 및 연락처를 확인하여 이전 번호가 다시 수집되는 것을 방지합니다. |
| 사용자 추가 필드 | 아니요 | 정책이 허용하는 경우 쿼리 공식에 포함될 수 있습니다. |

### 4.2 주소는 한 단계만 남음: 성/시

이전 계획에서는 주소 레벨 1과 레벨 2를 제안했습니다. V2는 해당 구분을 폐지했습니다.

V2는 하나의 구조화된 필드만 사용합니다:

```text
도
```

이 필드는 성 또는 중앙 직할시를 포함합니다.

예시:

```text
빈즈엉
호찌민
동나이
```

앱은 동, 면, 구, 군 또는 도로명을 필수 조건으로 사용하지 않습니다.

이유:

*   동, 면의 명칭은 합병 후 아직 안정적이지 않을 수 있습니다.
*   기존 데이터와 신규 데이터는 동일한 지역에 대해 두 가지 다른 명칭으로 기록될 수 있습니다.
*   산업 단지 내 회사는 특정 도로명이 없을 수 있습니다.
*   불확실한 도로명을 사용하면 올바른 URL을 잘못 제외할 수 있습니다.

입력 파일에 전체 주소가 있는 경우, 앱은 해당 문자열을 표시 및 보고서 출력용으로 그대로 유지합니다.

운영 부분은 시/도만 가져옵니다. 나머지 구성 요소는 쿼리를 차단하거나 URL을 자동으로 제외하는 데 사용되어서는 안 됩니다.

시/도에 여러 표기법이 있는 경우, 사용자는 별칭 테이블을 제공할 수 있습니다.

`Alias`는 서로 다른 표기법이지만 동일한 값으로 간주되는 것입니다.

예시:

```text
호찌민시
호찌민
호찌민시
```

위 세 가지 표기법은 `Hồ Chí Minh`으로 표준화될 수 있습니다.

앱이 시/도를 확실하게 식별하지 못하는 경우, 도로명이나 산업 단지명으로 스스로 추측하지 않습니다. 해당 입력 라인은 검토가 필요한 목록에 추가됩니다.

## 5. 플레이스홀더를 사용한 쿼리 공식

### 5.1 플레이스홀더란 무엇인가

`Placeholder`는 쿼리 공식 내의 빈 위치입니다. 실행 시 앱은 해당 위치를 각 회사의 실제 데이터로 대체합니다.

공식 예시:

```text
"{{vietnamese_name}}" "{{province}}" ({{contact_keywords}})
```

데이터:

```text
vietnamese_name = CÔNG TY TNHH MINH AN
province = Bình Dương
contact_keywords = "전화번호" OR "연락처" OR "contact"
```

실제 쿼리는 다음과 같습니다:

```text
"CÔNG TY TNHH MINH AN" "Bình Dương"
("전화번호" OR "연락처" OR "contact")
```

사용자가 공식을 결정합니다. 앱은 회사명이 먼저 와야 하는지 또는 세금 코드가 몇 번째 단계에서 실행되어야 하는지를 고정하지 않습니다.

### 5.2 두 가지 유형의 플레이스홀더

#### Company Input Profile에서 가져오는 플레이스홀더

`Company Input Profile`은 파이프라인 실행 전 회사의 표준화된 데이터입니다.

예시:

```text
{{company_name}}
{{vietnamese_name}}
{{tax_code}}
{{province}}
{{legal_representative}}
{{custom_input_field}}
```

입력 파일에 `factory_name` 열이 추가된 경우, 사용자는 `{{factory_name}}`이 쿼리에 나타나도록 허용할 수 있습니다.

#### 사용자가 선언한 고정 값 플레이스홀더

고정 값은 항상 재사용되는 키워드 그룹에 적합합니다.

예시:

```yaml
custom_values:
  contact_keywords: '"số điện thoại" OR "liên hệ" OR "contact"'
  recruitment_keywords: '"tuyển dụng" OR "việc làm"'
```

그 다음 쿼리는 다음을 사용합니다:

```text
"{{vietnamese_name}}" "{{province}}" ({{contact_keywords}})
```

사용자는 키워드 그룹을 한 곳에서만 수정합니다. 관련된 모든 쿼리는 다음 실행 시 자동으로 새 값을 가져옵니다.

### 5.3 각 공식은 필수 필드를 선언해야 합니다

예시:

```yaml
query_templates:
  - name: contact_by_vietnamese_name
    template: '"{{vietnamese_name}}" "{{province}}" ({{contact_keywords}})'
    required_fields:
      - vietnamese_name
      - province
```

회사에 `province`가 없는 경우, 앱은 너무 광범위한 이름 쿼리를 생성하지 않습니다.

쿼리의 작업 단위는 다음과 같이 기록됩니다:

```text
생략됨
사유: 필수 필드 'province' 누락
```

세금 코드가 있는 경우, 플래너는 다른 공식으로 전환할 수 있습니다:

```text
"{{tax_code}}"
```

`Planner`는 어떤 작업 단위가 생성되어야 하는지 결정하기 위해 입력과 정책을 읽는 블록입니다.

### 5.4 이름 기반 쿼리에는 시/도가 포함되어야 합니다

기본 정책은 다음 규칙을 적용합니다:

*   회사명 또는 베트남어 회사명이 포함된 쿼리에는 `{{province}}`가 동반되어야 합니다.
*   세금 코드만으로 구성된 쿼리는 시/도 없이 실행될 수 있습니다.
*   시/도도 없고 세금 코드도 없는 경우, 광범위한 이름 전용 쿼리는 실행되지 않습니다.

`Broad query`는 너무 광범위한 검색어입니다. 예를 들어, 지역 또는 식별 코드 없이 `"MINH AN"`만 있는 경우입니다.

데이터가 부족한 경우는 `dependency_missing`으로 기록됩니다 — 필요한 입력 정보가 부족하여 계속 실행할 수 없습니다.

### 5.5 앱은 실제 실행 전에 공식을 확인합니다

배치를 시작하기 전에, 앱은 미리 보기를 표시해야 합니다.

1,000개 회사에 대한 예시:

```text
920개 회사가 이름 + 시/도 기준으로 쿼리를 생성했습니다.
55개 회사가 세금 코드로 쿼리하도록 전환했습니다.
25개 회사는 시/도와 세금 코드 모두 누락되었습니다.
유효하지 않은 플레이스홀더는 0개입니다.
```

`{{provine}}`와 같이 잘못 작성된 플레이스홀더가 있는 경우, 앱은 API를 호출하기 전에 구성 오류를 보고합니다.

사전 확인은 잘못 생성된 수천 개의 쿼리에 대한 비용 지불을 방지하는 데 도움이 됩니다.

## 6. Source Policy: 소스 구성 및 우선순위

각 도메인 또는 도메인 그룹은 다음과 같이 구성할 수 있습니다:

*   어떤 티어에 속하는지.
*   우선순위.
*   검색 시 추가 점수.
*   스크랩 고려를 위한 최소 점수.
*   Cheap GET Preflight를 허용할지 여부.
*   스크랩 모드.
*   동적 페이지인 경우 대기해야 하는 Selector.
*   최대 워커 수.
*   API 재시도 횟수.
*   비용 제한.

`Cheap GET Preflight`는 유료 Firecrawl Scrape를 사용하기 전에 저렴한 요청으로 HTML을 로드하는 단계입니다.

현재 기본 순서:

1.  Business Directory.
2.  적합한 새 연락처가 아직 없는 경우, Job Portal로 전환합니다.
3.  여전히 적합한 새 연락처가 없는 경우, Facebook으로 전환합니다.

Saramin 또는 새 도메인은 정책에 추가하기만 하면 됩니다. 점수 매기기 블록이나 파이프라인을 수정할 필요가 없습니다.

예시:

```yaml
source_families:
  - name: yellowpages_network
    domains:
      - yellowpages.vn
      - yellowpages.com.vn
      - trangvangvietnam.com

promotion_name_probable_threshold: 0.90
promotion_evidence_similarity_threshold: 0.85

tiers:
  - name: authoritative_registry # 공식 등록 기관 출처. 이름이 일치하면 자체 확인 가능
    priority: 0
    scrape_mode: scrape_all_planned
    require_tax_code_match: true
    one_url_per_domain: true

  - name: tax_directory          # 세금 정보 조회/집계 출처. 교차 확인 필요
    priority: 1
    scrape_mode: scrape_all_planned
    require_tax_code_match: true
    one_url_per_domain: true

  - name: business_directory
    priority: 2
    scrape_mode: scrape_all_planned
    one_url_per_domain: true

  - name: job_portal
    priority: 3
    scrape_mode: stop_on_first_valid_phone
    one_url_per_domain: true

  - name: facebook
    priority: 4
    scrape_mode: stop_on_first_valid_phone
    one_url_per_domain: true
```

`scrape_all_planned`는 해당 티어에서 선택된 모든 URL을 스크랩한다는 의미입니다.

`stop_on_first_valid_phone`는 해당 티어에서 유효한 전화번호를 찾았을 때 새 URL 열기를 중단한다는 의미입니다.

각 티어는 고유한 모드를 선택할 수 있습니다.

`one_url_per_domain: true`는 동일한 도메인 내에서 가장 높은 점수를 받은 URL만 열린다는 것을 의미합니다. 모든 티어에 대해 기본적으로 활성화됩니다.

`authoritative_registry`와 `tax_directory`는 동등하게 간주되지 않습니다. 공식 등록 출처 또는 사용자가 명시적으로 `authoritative_registry`로 구성한 출처만이 자체적으로 프로모션을 지원할 수 있습니다. Masothue와 같은 통합 웹사이트는 `tax_directory`에 속하며, 여전히 교차 확인이 필요합니다.

`require_tax_code_match: true`는 연락처를 받을 때 위에 언급된 두 티어 모두에 적용됩니다. Masothue 웹사이트는 경로에 세금 코드를 포함하므로, 웹사이트의 세금 코드가 목표 세금 코드와 일치해야만 전화번호가 승인될 수 있습니다. 이 규칙은 V1에 이미 있었고 V2에서도 유지되어야 합니다. 이는 Masothue를 자체 검증 출처로 만들지 않습니다.

예시:

```text
목표 사업자등록번호: 3701234567
발견된 URL:      masothue.com/3709999999-cong-ty-minh-an
                                ^^^^^^^^^^ 다른 회사, 이름이 비슷함
→ 두 사업자등록번호가 다름 → URL 제외, 이유 기록: masothue_tax_mismatch
```

## 7. V2 실행 시 완전한 예시

아래 예시는 구체적인 예시 데이터를 사용하여 모듈들이 어떻게 협력하는지 보여줍니다.

### 7.1 입력

```text
회사명: 민안 유한책임회사
베트남어 이름: 민안 유한책임회사
성/시: 빈즈엉
세금 코드: 3701234567
대표자: 응우옌 반 아

블랙리스트:
- 0901111222, 라벨 = wrong_num
- 0274388888, 라벨 = same_num
```

앱은 `wrong_num`과 `same_num`을 사용자가 제공한 레이블로만 이해합니다.

앱은 어떤 번호가 틀렸는지, 유효하지 않은지 또는 중복되는지 스스로 결론을 내리지 않습니다. 그러한 평가는 입력하기 전에 사용자에 의해 수동으로 확인되었습니다.

### 7.2 쿼리 생성 및 실행

쿼리 1:

```text
"MINH AN 유한책임회사" "빈즈엉"
("전화번호" OR "연락처" OR "contact")
```

Firecrawl Search는 8개의 URL을 반환합니다. 점수 매긴 후, 4개의 URL이 35점 이상을 받았습니다.

쿼리 2:

```text
"3701234567"
```

쿼리 2는 추가로 10개의 URL을 반환합니다. 6개의 새로운 URL이 35점 이상을 받았습니다.

총 10개의 고품질 URL이 확보되었습니다. 플래너는 새로운 쿼리 생성을 중단하고 URL 검사 단계로 넘어갑니다.

### 7.3 URL 점수 매기기 및 분류

각 URL은 세 그룹 중 하나로 분류됩니다.

- `Accepted`: 다음 단계로 진행할 자격이 있습니다.
- `Deferred`: 신호는 있지만 충분히 확실하지 않아 사용자 검토가 필요합니다.
- `Rejected`: 점수가 너무 낮거나 명확한 모순이 있습니다.

예시:

```text
10개 URL 승인됨
2개 URL 보류됨
6개 URL 거부됨 또는 임계값 미달
```

`Deferred`는 오류가 아닙니다. 이는 증거가 아직 약하기 때문에 앱이 스스로 결정해서는 안 되는 경우를 위한 대기열입니다.

두 개의 지연된 URL은 다른 회사들을 차단하지 않습니다. 워커는 사용자 검토를 기다리는 동안 다음 회사를 계속 처리합니다.

### 7.4 Cheap GET 사전 점검

승인된 10개의 URL 중, 정책은 비즈니스 디렉토리에 속하는 4개의 URL에 대해 저렴한 GET을 허용합니다.

`Metadata`는 검색에서 이미 얻은 요약 정보로, 주로 URL, 페이지 제목 및 설명 부분을 포함합니다.

결과:

```text
URL 1에 0901111222 포함 → URL 1 건너뛰기
URL 2에 블랙리스트 포함하지 않음 → 통과
URL 3에 블랙리스트 포함하지 않음 → 통과
URL 4가 GET에 응답하지 않음 → 메타데이터 검색 확인
```

`Regex`는 텍스트에서 문자 패턴을 찾는 방법입니다. 여기서는 regex가 정확히 동일한 블랙리스트 번호의 다른 표기법을 찾는 데만 사용됩니다.

예를 들어 `0901111222`, `0901 111 222`, `0901-111-222`는 동일한 값을 비교하기 위해 표준화될 수 있습니다.

URL 4의 제목과 설명에 블랙리스트가 포함되어 있지 않지만 정보가 충분하지 않더라도, URL은 이전에 점수를 받았기 때문에 여전히 스크랩됩니다.

블랙리스트 일치는 현재 검사 중인 URL만 건너뜁니다. 전체 회사를 건너뛰지 않습니다.

### 7.5 병렬 스크랩 및 소프트 스톱

스크랩 가능한 URL이 9개 남아 있고 티어가 `stop_on_first_valid_phone` 모드를 사용한다고 가정합니다.

세 명의 워커가 처음 세 개의 URL을 받습니다.

`Concurrency`는 동시에 실행되는 작업의 수입니다. 이 예시에서는 동시성이 3입니다.

결과:

```text
작업자 1: 0274388888 발견함 → 블랙리스트와 일치함, same_num 레이블 지정함
작업자 2: 0912345678 발견함 → 유효한 새 번호
작업자 3: 실행 중 → 완료 및 결과 저장이 허용됨
남은 6개 URL: 아직 열리지 않음 → 정책에 따라 중지됨
```

`Soft stop(소프트 스톱)`은 새로운 작업을 시작하지 않지만, 거의 완료된 URL을 중단하지 않는다는 것을 의미합니다.

즉시 중단하면, 앱은 스크랩 크레딧을 소모했을 수 있지만 결과를 저장할 시간이 없었을 수 있습니다.

이 예시에서 앱은 9개 URL 중 3개만 열었습니다. 각 URL이 하나의 스크랩 크레딧을 소모한다면, 앱은 이 티어에서 최대 6개의 크레딧을 절약할 수 있습니다.

### 7.6 AI 호출 전 콘텐츠 자르기

Firecrawl은 25,000자 길이의 Markdown 페이지를 반환합니다.

`Markdown`은 제목, 단락, 목록 및 표를 포함하는 텍스트로 간소화된 웹 페이지 콘텐츠 버전입니다.

`Context Slicing`은 AI에 보내기 전에 회사 식별 데이터에 가까운 단락을 잘라내는 것입니다.

앱은 `anchor`(앵커), 즉 세금 코드, 법적 이름 또는 대표자와 같은 기준점을 찾습니다.

예시:

```text
[유지] 민안 유한책임회사, 세금 코드 3701234567, 빈즈엉에 위치...
[유지] 회사 연락처: 0912345678...
[제외]  편집부 광고 문의: 0289999999...
```

자른 후, AI는 25,000자 대신 1,800자만 받습니다.

이 예시에서 AI에 전송되는 텍스트 양은 약 92.8% 감소합니다.

Context Slicing은 AI 토큰을 절약하고 잘못된 푸터를 가져올 가능성을 줄입니다. 사용된 스크랩 크레딧을 환불하지 않으므로, Cheap GET은 여전히 먼저 실행되어야 합니다.

### 7.7 결과 저장

각 연락처는 다음 정보와 함께 저장됩니다.

- 연락처 값.
- 소스 URL.
- 연락처를 포함하는 단락.
- 페이지에 게시된 경우 게시일.
- 앱 스크랩일.
- 블랙리스트 비교 결과.
- 승인 또는 거부 이유.

예시:

```text
0912345678
source_url: https://example-directory.vn/minh-an
published_date: 2026-06-15
blacklist_match: false
decision: valid_contact
```

페이지에 게시일이 없으면, `published_date` 필드는 비워집니다. 앱은 스크랩 날짜를 게시일인 것처럼 위장하기 위해 사용하지 않습니다.

전체 순서:

| 순서 | 단계 | 비용 발생 여부 |

| 2 | 실행 구성 캡처 | 아니요 |
| 3 | **Gemini Quick Search — 세금 코드, 베트남어 회사명, 주소 보충** | 예 |
| 4 | 쿼리 계획 수립 | 아니요 |
| 5 | 검색 캐시 확인 | 아니요 |
| 6 | 품질 URL이 충분할 때까지 검색 | 예 |
| 7 | URL 점수 매기기, 도메인 중복 제거, 세금 코드 확인 | 아니요 |
| 8 | 사용자 Deferred 검토 | 아니요 |
| 9 | **Business status gate — 회사 활동 여부 확인** | 예 |
| 10 | 저비용 GET 및 메타데이터 폴백 | 매우 저렴 |
| 11 | 티어별 스크랩 계획 수립 | 아니요 |

| 13 | 컨텍스트 자르기 및 추출 | 예 |
| 14 | 블랙리스트 비교 및 ​​종합 | 아니요 |
| 15 | 티어 종료 또는 다음 티어 시작 | 아니요 |
| 16 | 종합 상태 계산 | 아니요 |

두 개의 굵은 글씨 단계는 V1에 이미 존재하지만 이전 계획에서 누락되었던 단계입니다.

### 단계 1 — 입력값 읽기 및 표준화

앱은 이름, 세금 코드, 성/시, 대표자 및 블랙리스트 전화번호를 표준화합니다.

전체 주소 문자열은 표시를 위해 유지됩니다. 성/시만 구조화된 주소 필드로 사용됩니다.

### 단계 2 — 실행 구성 캡처

앱은 Source Policy, 쿼리 공식 및 입력값의 버전을 저장합니다.

### 단계 3 — Gemini Quick Search

앱은 회사의 식별 정보를 조회하기 위해 Google Search Grounding을 호출합니다.

이 단계는 누락된 필드인 세금 코드, 베트남어 회사명, 주소, 대표자를 채웁니다.

결과는 Gemini가 출처로 사용한 URL과 함께 **회사 수준** 연락처로 저장됩니다.

앱은 무료 한도를 초과하지 않도록 하루 사용 횟수를 계산합니다.

Gemini가 출처로 사용한 URL은 동일한 페이지에 대해 두 번 비용을 지불하지 않도록 다음 단계의 검색 결과에서 제외됩니다.

이 단계가 실패하더라도 앱은 원본 입력 데이터를 사용하여 계속 진행합니다. 이는 차단 오류가 아닙니다.

### 단계 4 — 쿼리 계획 수립

플래너는 플레이스홀더를 실제 데이터로 대체합니다.

각 쿼리는 사용된 필드를 명확히 기록합니다. 이 목록은 중복 점수 계산을 피하기 위해 URL 점수 매기기 블록으로 전달됩니다.

### 단계 5 — 검색 캐시 확인

`Provider`는 Firecrawl이 검색 및 스크랩을 제공하는 것과 같이 작업을 수행하는 외부 서비스입니다.

앱은 쿼리, provider, 옵션 및 버전 정책으로부터 `fingerprint` — 즉 지문을 생성합니다.

두 요청은 fingerprint가 동일할 때만 동일한 것으로 간주됩니다.

캐시 히트는 이전 결과를 반환하고 검색 비용을 0으로 기록합니다. 앱은 Search Result URL을 다시 삽입하지 않습니다.

### 단계 6 — 품질 URL이 충분할 때까지 검색

쿼리는 정책에 명시된 순서대로 실행됩니다.

점수가 35점 이상인 URL이 10개 충분하면 플래너는 검색 단계를 종료합니다. 아직 실행되지 않은 쿼리는 `cancelled_by_policy`로 표시됩니다.

이 상태는 쿼리가 더 이상 필요하지 않음을 의미하며, 쿼리 오류가 아닙니다.

### 단계 7 — URL 점수 매기기, 도메인 중복 제거 및 세금 코드 확인

점수 매기기 블록은 쿼리에서 아직 사용되지 않은 도메인, 제목, 설명 및 증거를 검토합니다.

`Evidence`는 URL이 올바른 대상 회사에 속한다는 증거입니다.

세금 코드가 해당 쿼리의 주요 필드로 사용되지 않은 경우, 정확한 세금 코드는 매우 강력한 증거가 될 수 있습니다.

세 가지 작업이 순서대로 수행됩니다:

1.  블랙리스트 도메인 및 뉴스 도메인을 즉시 제거합니다.
2.  3.7항과 같이 `match`, `mismatch`, `unknown` 세 가지 결과에 따라 세금 코드를 확인합니다. `mismatch`만 URL을 제거합니다.
3.  점수를 매긴 후, 각 도메인에서 **가장 높은 점수를 받은 URL 하나만** 유지합니다.

URL은 accepted, deferred 또는 rejected로 분류됩니다. 각 URL은 사용자가 확인할 수 있도록 상세 점수표를 유지합니다.

도메인 중복으로 인해 제거된 URL은 `duplicate_domain` 이유와 함께 여전히 저장됩니다. 데이터베이스에서 삭제되지 않으므로 내보내기 시 추적할 수 있습니다.

### 단계 8 — 사용자 Deferred 검토

사용자는 개별 URL 또는 여러 URL을 선택한 다음 다음을 클릭할 수 있습니다:

-   Scrape.
-   Skip.
-   Keep deferred.

결정은 저장됩니다. 재개 시 앱은 이미 처리된 URL에 대해 다시 묻지 않습니다.

### 단계 9 — Business status gate

모든 URL을 열기 전에 앱은 법적 출처 페이지를 스크랩하여 활동 상태를 읽습니다.

회사가 일시 중단, 해산, 세금 코드 폐쇄 또는 파산 대기 중인 경우:

```text
회사가 완료 상태로 종료되었습니다.
stop_reason: business_status_inactive
추가로 스크랩된 URL 수: 0
```

“등록된 주소에서 활동하지 않음” 상태는 중단 조건이 아닙니다. 해당 회사는 정상적으로 계속 운영됩니다.

상태를 읽을 수 없는 경우 앱은 계속 진행합니다. 결론이 없다는 것은 차단하지 않는다는 의미입니다.

### 단계 10 — 저비용 GET 및 메타데이터 폴백

앱은 정책에서 허용하는 도메인만 GET합니다.

`Fallback`은 예비 방법입니다. GET이 응답하지 않으면 앱은 검색 결과에서 URL, 제목 및 설명을 사용합니다.

메타데이터가 여전히 불충분하지만 URL이 이미 accepted된 경우, 앱은 스크랩으로 전환합니다.

### 단계 11 — 티어별 스크랩 계획 수립

티어는 선택된 모든 URL을 스크랩하거나 첫 번째 유효한 숫자가 있을 때 중단할 수 있습니다.

워커는 pending 상태인 Scrape Work Unit만 받습니다.

`Pending`은 작업이 생성되었지만 아직 어떤 워커도 처리하지 않았음을 의미합니다.

### 단계 12 — 도메인별 대기 시간으로 스크랩

일반 페이지는 Firecrawl의 스마트 대기 및 `waitFor=0`을 사용합니다.

동적 페이지는 도메인에 자체 구성이 있는 경우에만 selector를 기다립니다.

현재 API에 해당 필드가 없으므로 앱은 `waitUntil: networkidle`을 Batch Scrape의 일반 옵션으로 보내지 않습니다.

### 단계 13 — 컨텍스트 자르기 및 추출

`Extract`는 선택된 콘텐츠 부분에서 전화번호, 이메일 또는 등록일과 같은 구조화된 데이터를 추출하는 것입니다.

AI는 Context Slice만 받으며, 페이지의 처음 15,000자를 고정적으로 받지 않습니다.

연락처는 저장된 증거 단락에 연락처 문자열이 나타날 때만 허용됩니다.

### 단계 14 — 블랙리스트 비교 및 ​​종합

전화번호는 표준화된 후 해당 회사의 블랙리스트와 비교됩니다.

일치하는 경우, 앱은 사용자가 제공한 레이블을 다시 할당합니다. 앱은 `wrong_num`, `invalid_num`, `same_num` 또는 사용자 지정 레이블을 자동으로 변경하지 않습니다.

### 단계 15 — 티어 종료 또는 다음 티어 시작

티어가 목표를 달성한 경우, 아직 열리지 않은 작업 단위는 정책에 따라 닫힙니다.

티어에 새 연락처가 없는 경우, 플래너는 다음 티어를 엽니다.

### 단계 16 — 종합 상태 계산

앱은 저장된 작업 단위와 시도 횟수를 읽어 회사의 상태 카드를 생성합니다.

앱은 모든 의미에 대해 단일 상태를 사용하지 않습니다.

## 9. V2의 기능 블록

아래 각 행은 개별적으로 테스트할 수 있는 모듈입니다.

`Artifact`는 저장된 원본 결과물로, 예를 들어 검색 결과 세트 또는 마크다운 페이지입니다.

`컨택트 관찰`은 URL에서 방금 관찰된 컨택트입니다. 이는 블랙리스트 및 통합 단계를 거치기 전의 최종 결과가 아닙니다.

`Attempt`는 워커가 Work Unit을 실행하려고 시도한 한 번의 행위입니다.

`작업 로그`는 추가만 기록하는 이력 기록부입니다. 이는 어떤 작업이 생성되었는지, 누가 받았는지, 몇 번 시도되었는지, 그리고 최종 결과가 무엇인지를 저장합니다. 이는 조회 및 설명을 위해 사용되며, 현재 상태를 계산하는 데 사용되지 **않습니다**.

### 9.1 모듈 분할 원칙

각 파일은 한 가지 일만 합니다. 작은 파일은 수정하기 쉽고, 테스트하기 쉬우며, 다른 부분을 손상시키지 않고 AI에게 수정을 요청하기 쉽습니다.

규칙:

- 한 파일은 대략 200줄을 초과하지 않습니다.
- 비용이 드는 API를 호출하는 파일은 동시에 데이터베이스에 기록해서는 안 됩니다.
- 비즈니스 로직을 결정하는 파일은 API를 호출해서는 안 됩니다.
- 모든 파일은 데이터를 입력받고 데이터를 출력하며, 전역 설정을 직접 읽지 않습니다.

중요한 이유: 실제 테스트 후에는 비즈니스 로직 변경이 여러 번 있을 것입니다. 로직이 큰 파일 안에 흩어져 있다면, 변경할 때마다 여러 곳을 수정해야 하고 새로운 오류가 발생하기 쉽습니다.

V2 코드는 새 패키지 안에 있으며, 각 부분을 점진적으로 전환하기 위해 V1 코드 옆에 배치됩니다.

  identity/

### 9.3b 병렬 실행 부분은 다음 배포로 연기

1차 배포에서는 새로운 워커 풀과 런타임 슈퍼바이저를 구축하지 **않습니다**.

이유: V1의 다중 워커 실행 메커니즘이 현재 작동하고 있습니다. 이는 안전한 작업 수신, 하트비트, 중단된 워커의 작업 회수 및 안전 지점에서의 중지 기능을 이미 갖추고 있습니다.

1차 배포에서는 해당 메커니즘을 그대로 사용합니다:

| 부분 | 1차 배포 | 다음 배포 |
|---|---|---|
| 작업 대기열 | V1의 `pipeline_jobs` 사용 | 작은 work unit으로 변경 |
| 작업 수신, 하트비트 | V1의 것을 그대로 사용 | 그대로 유지, 세부 수준만 변경 |
| Pause, resume, drain, shutdown | V1의 것을 그대로 사용 | `runtime/supervisor.py`로 분리 |
| 동시 실행 워커 수 | 현재와 같이 유지 | 정책에 따라 조정 |

`src/v2/`의 새로운 비즈니스 모듈은 **병렬 실행 방식에 의존하지 않도록** 작성되었습니다. 각 모듈은 데이터를 입력받아 데이터를 출력합니다. 따라서 다음 배포에서 새로운 워커로 변경할 때 비즈니스 모듈을 수정할 필요가 없습니다.

속도가 충분하지 않거나 동일한 회사 내에서 여러 작은 작업을 병렬로 실행해야 하는 등 명확한 이유가 있을 때만 새로운 워커로 전환합니다.

### 9.4 상태는 행에 저장되며, 이력에서 다시 계산되지 않습니다.

이전 계획은 전체 `Work Ledger`를 다시 읽어 회사 상태를 계산할 것을 제안했습니다.

그 방식은 느리고 오류를 찾기 매우 어렵습니다.

V2는 더 간단한 방식을 사용합니다:

- 현재 상태는 work unit 행에 직접 저장됩니다.
- `Work Log`는 이력 조회 및 설명을 위한 것이며, 상태 계산의 소스가 아닙니다.

작업 수신 방식은 현재 실행 중인 V1의 메커니즘을 그대로 사용합니다: 짧은 트랜잭션 내에서 조건부 업데이트 문을 사용합니다.

```text
UPDATE work_units SET owner = :worker, claimed_at = now
WHERE id = :id AND status = 'pending'
```

두 워커가 동시에 이 문장을 실행하면 한 워커만 업데이트할 수 있습니다. 나머지 워커는 다른 작업을 받습니다.


## 10. 검색 캐시 및 중복 데이터 방지

### 10.1 89,070개 중복 행의 실제 원인

V1에서는 캐시에서 결과를 가져온 후 외부 스레드가 저장 함수를 한 번 더 호출했습니다. 데이터베이스에 중복 행을 차단하는 장벽이 없었기 때문에 이 오류가 점진적으로 누적되었습니다.

89,070개의 모든 중복 행은 **동일한 회사 내**에서 중복된 것이며, 회사 간에 중복된 것이 아닙니다.

### 10.2 수정하기 위한 두 가지 변경 사항

**변경 사항 1 — 캐시 히트 버그 수정.**

```text
캐시 히트 → 이전 결과 반환 → 비용이 0임을 알리는 cache_reused 이벤트 기록
         → 검색 결과 저장 함수를 더 이상 호출하지 않음
```

**변경 사항 2 — 데이터베이스에 장벽 추가.**

`Unique key`는 동일한 식별자를 가진 두 행이 중복 저장되는 것을 허용하지 않는 데이터베이스 규칙입니다.

```text
search_results 테이블에서 UNIQUE (company_id, search_query, url)
```

이 변경 후에는 중복 행이 데이터베이스에 의해 거부됩니다. 이후 코드가 잘못 작성되더라도 오류가 다시 발생할 수 없습니다.

**수반되는 작업:** unique key를 추가하기 전에 기존 89,070개의 중복 행을 정리하는 스크립트를 실행합니다. 정리하지 않으면 추가할 수 없습니다.

### 10.3 작업 단위에 대한 멱등성 키

`Idempotency key`는 작업 단위의 코드로, 동일한 작업을 다시 호출해도 하나의 결과만 생성되도록 돕습니다.

예를 들어, 두 워커가 동일한 쿼리에서 캐시 미스를 동시에 겪는 경우:

```text
Worker 1과 Worker 2는 회사 A를 위한 쿼리 Q의 결과를 함께 저장하려고 합니다.
고유 키는 한 워커가 성공적으로 저장할 수 있도록 합니다.
나머지 워커는 사본을 생성하는 대신 이미 저장된 결과를 다시 읽습니다.
```

### 10.4 왜 “공유 결과 세트” 설계를 사용하지 않는가

이전 계획은 각 검색 결과를 한 번만 저장하고, 회사들이 해당 세트를 참조하도록 제안했습니다.

이 제안은 실제 데이터베이스에서 측정 후 폐기되었습니다:

| 내용 | 비율 |
|---|---:|
| 동일 회사 내 중복 — 실제 버그 | 8.5% |
| 여러 회사가 공유하는 쿼리 — 공유 설계로 절약할 수 있는 최대치 | 2.1% |

21,041개의 쿼리 중 164개만이 두 개 이상의 회사에서 사용되었는데, 이는 쿼리에 회사 이름이 포함되어 있기 때문입니다.

공유 설계는 또한 두 가지 추가 위험을 초래합니다:

1.  각 회사는 동일한 URL에 대해 자체적인 결정을 내립니다. 예를 들어, 회사 A는 URL 번호 3을 제외하고, 회사 B는 URL 번호 3을 스크랩하여 전화번호를 찾습니다. 이러한 결정은 공유 세트에 저장할 공간이 없으므로 별도의 테이블을 추가해야 합니다. 그리고 그 테이블은 현재 테이블과 동일하게 각 회사와 각 URL에 대해 정확히 하나의 행을 가집니다.
2.  데이터베이스는 현재 다른 곳에서 참조 중인 데이터 삭제를 차단하는 메커니즘이 활성화되어 있지 않습니다. 원본 결과 세트를 삭제하면 여러 회사의 데이터가 참조를 잃게 됩니다.

10.2항의 두 가지 변경 사항은 정확히 8.5%를 해결하며 새로운 위험을 생성하지 않습니다.

## 11. 재시도 및 API 오류 처리

V2는 총 호출 횟수와 재시도 횟수 간의 오해를 피하기 위해 `max_attempts`라는 이름을 사용합니다.

권장 구성:

```yaml
retry:
  max_attempts: 3
  base_delay_seconds: 2
  max_delay_seconds: 60
  honor_retry_after: true
  jitter: true
```

`max_attempts: 3`은 최대 세 번 호출을 의미합니다: 첫 번째 호출과 최대 두 번의 재시도.

만약 비즈니스 로직이 “첫 번째 호출에 세 번의 재시도 추가”를 원한다면, 정책은 `max_attempts: 4`로 설정합니다.

### 재시도 가능한 오류

-   타임아웃 또는 HTTP 408.
-   일시적인 연결 손실.
-   공급자가 반환한 `Retry-After` 시간에 따른 HTTP 429.
-   오류가 일시적일 가능성이 있는 경우 HTTP 500, 502, 503 또는 504.

### 재시도 불가능한 오류

-   잘못된 요청으로 인한 HTTP 400.
-   잘못된 API 키로 인한 HTTP 401.
-   크레딧 소진으로 인한 HTTP 402.
-   입력에 필수 필드 누락.
-   잘못된 플레이스홀더 구성.

`Backoff`는 각 오류 발생 후 점진적으로 증가하는 대기 시간입니다.

예시:

```text
첫 번째 오류 → 약 2초 대기
두 번째 오류 → 약 4초 대기
세 번째도 여전히 오류 → 정책에 따라 작업 단위 중지
```

`Jitter`는 작은 무작위 대기 시간입니다. 이는 20개의 워커가 동시에 API를 다시 호출하는 것을 방지합니다.

각 시도는 작업 로그에 기록됩니다. 재시도는 실패한 API 작업만 다시 실행하며, 전체 회사를 다시 실행하지 않습니다.

종료 명령은 백오프 시간을 중단할 수 있습니다. 워커는 60초를 다 기다리지 않고 종료될 수 있습니다.

## 12. 더 빠르지만 통제된 스크래핑

이 섹션에서는 Firecrawl Scrape 호출 시 네 가지 조정 매개변수에 대해 설명합니다.

```yaml
firecrawl:
  wait_for_ms: 0
  only_main_content: true
  max_age_ms: policy_controlled
  max_concurrency: policy_controlled
```

### 12.1 `wait_for_ms` — 페이지를 읽기 전에 추가로 얼마나 기다릴 것인가

Firecrawl은 이미 페이지 로드를 기다립니다. `wait_for_ms`는 그 이후에 **추가되는** 대기 시간입니다.

V1은 모든 페이지에 3,000ms를 설정했습니다. 이는 페이지가 이미 준비되었더라도 모든 페이지에 3초가 추가된다는 의미입니다.

```text
20개 URL × 3초 = 각 회사당 60초의 불필요한 대기 시간
1,000개 회사 → 약 16시간의 불필요한 대기 시간
```

V2는 `wait_for_ms: 0`으로 설정합니다. JavaScript로 페이지 로드가 느린 도메인만 별도로 구성됩니다.

### 12.2 `only_main_content` — 주요 콘텐츠 부분만 가져오기

활성화하면 Firecrawl은 메뉴, 헤더, 푸터를 제거하고 페이지 본문만 반환합니다.

```text
끄기: 25,000자 — 메뉴, 광고, 바닥글에 있는 편집부 핫라인 번호 포함
켜기: 8,000자 — 콘텐츠 부분만
```

두 가지 이점: AI 토큰 감소, 그리고 AI가 웹사이트 푸터에서 전화번호를 가져올 위험 감소.

이것은 첫 번째 보호 계층입니다. 7.6항의 Context Slicing은 두 번째 계층입니다.

### 12.3 `max_age_ms` — Firecrawl에 저장된 페이지 버전 재사용 허용

Firecrawl은 이전에 로드된 페이지 버전을 유지합니다. `max_age_ms`는 얼마나 오래된 버전까지 재사용할 수 있는지 지정합니다.

오래된 버전을 사용하면 다시 로드하는 것보다 저렴하고 빠릅니다.

```text
max_age_ms: 604800000  (7일)
→ Firecrawl이 지난 7일 이내의 페이지 사본을 보유하고 있으면 해당 사본을 반환

max_age_ms: 0
→ 항상 웹사이트에서 다시 다운로드
```

소스 유형별 설정 방법:

| 소스 유형 | 설정 값 | 이유 |
|---|---|---|
| 기업 디렉토리 페이지 | 7일 ~ 30일 | 전화번호는 거의 변경되지 않음 |
| 채용 페이지 | 1일 ~ 3일 | 채용 공고는 빠르게 변경됨 |
| 상태 게이트에 사용되는 법률 소스 페이지 | 0 | 최신 운영 상태 필요 |

### 12.4 `max_concurrency` — 동시에 몇 개의 URL을 열 것인가

동시에 여러 URL을 열면 더 빠르지만, 너무 빠르게 호출하면 Firecrawl이 차단합니다.

`HTTP 429`는 “너무 많이 호출했습니다. 기다려주세요”라는 응답입니다 — 17.3항을 참조하십시오.

앱은 무한정으로 동시 작업 수를 늘리지 않습니다. 차단되면 스스로 감소하고, 안정되면 점진적으로 다시 증가합니다.

실제 진행 상황 예시:

```text
8개 URL을 동시에 열고 있습니다
→ Firecrawl이 "30초 대기"와 함께 429를 반환합니다
→ 앱이 정확히 30초를 기다립니다
→ 앱이 동시에 4개 URL로 줄입니다
→ 20개의 연속 요청이 성공합니다
→ 앱이 동시에 5개, 그리고 6개 URL로 늘립니다
→ 만약 다시 429가 발생하면 계속 줄입니다
```

이 방식은 사용자가 고정된 숫자를 추측하게 하는 대신, 공급업체가 허용하는 최고 속도를 유지합니다.

### 12.5 Cheap GET의 자체 제한

7.4항의 Cheap GET Preflight는 Firecrawl을 거치지 않고 사용자 기기에서 직접 진행됩니다.

이는 웹사이트가 사용자의 IP 주소를 본다는 의미입니다. 너무 빠르게 호출하면 웹사이트가 해당 IP를 차단할 수 있습니다.

따라서 Cheap GET은 Firecrawl의 `max_concurrency`보다 훨씬 낮게 설정된 도메인별 자체 제한을 가집니다.

```yaml
cheap_get:
  max_concurrent_per_domain: 1
  min_delay_between_requests_ms: 1000
```

## 13. 지연 검토 화면

지연 화면은 올바를 가능성이 있지만, 앱이 자체적으로 스크랩 비용을 지불할 만큼 충분한 증거가 없는 URL을 위한 것입니다.

각 URL은 다음을 표시합니다:

- 회사명 및 시/도.
- URL, 도메인 및 티어.
- 검색 결과의 제목 및 설명.
- URL을 생성한 쿼리.
- 쿼리에 사용된 필드.
- 발견된 증거.
- 총점 및 상세 점수.
- 지연된 이유.
- 확인된 경우 GET 결과 또는 메타데이터.
- 예상 스크랩 비용.

사용자는 개별 URL 또는 여러 URL을 선택한 다음 다음으로 표시할 수 있습니다:

- Scrape.
- Skip.
- Keep deferred.

사용자가 즉시 검토하지 않으면, 대기 중인 회사 또는 티어만 해당 체크포인트에 유지됩니다.

다른 회사들은 계속 실행됩니다. 전체 파이프라인은 중단되지 않습니다.

## 14. 시스템 전체 중지, 일시 중지 및 재개

V2에는 네 가지 별도 명령이 있습니다:

| 명령 | 실제 동작 |
|---|---|
| Pause scheduling | 새 작업을 더 이상 발행하지 않으며, 실행 중인 작업은 안전 지점까지 진행할 수 있습니다. |
| Resume | 워커는 보류 중인 작업 단위를 계속 수신합니다. |
| Drain and shutdown | 새 작업을 수신하지 않고, 현재 작업이 저장될 때까지 기다린 후 워커를 종료합니다. |
| Emergency shutdown | 즉시 중지를 요청하며, 안전 시간이 지나면 프로세스를 종료합니다. |

`Drain`은 새 작업을 수신하지 않지만, 현재 진행 중인 작업이 저장될 때까지 기다린 후 종료하는 것을 의미합니다.

`Emergency shutdown`은 빠르게 종료해야 할 때만 사용됩니다. 결과가 커밋되지 않은 작업 단위는 작업 유지 권한이 만료된 후 보류 상태로 돌아갑니다.

여기서 `Commit`은 결과가 데이터베이스에 성공적으로 저장되었음을 확인받았다는 의미입니다.

각 워커는 다음을 가집니다:

- `Lease`: 제한된 시간 동안 작업 단위를 유지할 권한.
- `Heartbeat`: 워커가 살아있음을 알리는 주기적인 신호.

워커가 죽으면 하트비트가 중단됩니다. 리스가 만료되면 작업 단위는 다른 워커가 계속할 수 있도록 대기열로 돌아갑니다.

대시보드는 데이터베이스의 상태 하나가 변경되었다는 이유만으로 “중지됨”이라고 자체적으로 결론 내리지 않습니다.

`Runtime Supervisor`는 실제 프로세스, PID, 하트비트 및 작업 리스를 확인합니다.

`PID`는 운영 체제에서 실행 중인 프로세스의 식별자입니다.

### 시스템 중지 확인 조건

- 더 이상 워커 프로세스가 없습니다.
- 더 이상 새로운 하트비트가 없습니다.
- 허용된 시간 이후 새로운 API 호출이 없습니다.
- 미완료 작업 단위가 완료로 표시되지 않습니다.
- 재개 시, 보류 중이거나 리스가 만료된 작업 단위만 다시 수신됩니다.

## 15. 회사 상태 카드

V2는 모든 문제를 설명하기 위해 단일 상태를 사용하지 않습니다.

상태 카드는 이력에서 다시 계산하는 것이 아니라, 회사의 작업 단위에 저장된 현재 상태에서 읽어옵니다:

| 그룹 | 예시 | 답변되는 질문 |
|---|---|---|
| 실행 | running, paused, blocked, completed | 시스템이 계속 실행될 수 있습니까? |
| 커버리지 | not_started, partial, complete | 계획의 작업 단위가 어디까지 처리되었습니까? |
| 연락처 | none, found, verified | 연락처와 증거가 발견되었습니까? |
| 리소스 | available, credit_exhausted, rate_limited | API 호출을 계속할 수 있습니까? |
| 중지 이유 | user_stop, budget, api_error, dependency_missing | 왜 더 이상 진행되지 않습니까? |
| 최신성 | current, stale | 결과가 현재 입력 및 정책과 일치합니까? |

예시:

```text
paused
coverage: partial
contacts: found
resources: credit_exhausted
stop_reason: budget
```

대시보드 해석:

```text
Contact를 찾았습니다.
처리되지 않은 URL이 7/20개 남아있습니다.
계속하려면 크레딧을 충전해야 합니다.
```

크레딧이 있을 때, 플래너는 나머지 7개의 URL만 다시 엽니다.

`Completed`는 선택된 계획의 모든 작업 단위가 종료 상태에 있음을 의미할 뿐입니다.

Completed는 “연락처를 찾았다”는 의미와 동의어가 아닙니다.

유효한 수를 충분히 찾았기 때문에 중지된 작업 단위는 `cancelled_by_policy`로 종료될 수 있습니다. 이것은 여전히 유효한 종료 상태입니다.

## 16. 복사된 코드베이스에 대한 점진적 수정 로드맵

`Application service`는 인터페이스와 비즈니스 모듈 사이에 위치한 공통 처리 계층입니다. 덕분에 대시보드와 명령줄이 서로 다른 두 가지 중지/재개 방식을 자체적으로 작성하지 않습니다.

### 16.1 로드맵 원칙

- **각** 단계 후에 앱은 처음부터 끝까지 한 회사를 완전히 실행할 수 있어야 합니다. 어떤 단계도 시스템을 손상된 상태로 남겨두지 않습니다.
- 새 코드는 `src/v2/`에 있습니다. 이전 V1 코드는 새 부분이 테스트되고 실제로 실행된 후에만 삭제됩니다.
- 각 단계는 V1의 `replay mode`를 사용하여 저장된 데이터에서 다시 실행하며, API 비용을 소모하지 않습니다.
- 모든 단계에서 동일한 30개 샘플 회사 세트로 테스트합니다.

`Replay mode`는 비용이 드는 API를 호출하지 않고 저장된 데이터에서 전체 흐름을 다시 실행하는 모드입니다. V1에는 이미 이 모드가 있었고, V2는 이를 주요 테스트 도구로 사용합니다.

### 16.2 단계

| 단계 | 수행 내용 | 확인 필요 결과 |
|---|---|---|
| 0. 샘플 세트 선택 | 이름은 같지만 다른 성/시의 회사, 뉴스 페이지, 타임아웃, 캐시 히트, 블랙리스트, 해산된 회사, 성/시 정보가 없는 회사 등 30개 회사를 선택합니다. V1을 실행하고 결과를 저장합니다. | 향후 비교를 위한 V1 결과 세트가 있어야 합니다. |
| 1. 가장 저렴한 세 가지 오류 수정 | `waitFor: 3000` 제거, `DELAY_SECONDS`를 0으로 설정, 캐시 히트 버그 수정, 중복 행 정리, 고유 키 추가, `max_attempts`를 사용한 최소 재시도 실행기 생성 및 5xx 오류 분류. | 정적 페이지가 더 이상 고정적으로 대기하지 않습니다. 캐시 히트가 새 행을 생성하지 않습니다. 503,503,200 시퀀스가 세 번째 시도에서 성공합니다. |
| 2. API를 호출하지 않는 모듈 분리 | `input/`, `policy/`, `identity/taxcode.py`. 아직 실행 흐름을 변경하지 않았습니다. | 각 파일을 개별적으로 실행할 수 있습니다. 세금 코드가 올바른 일치/불일치/알 수 없음 결과를 반환합니다. |
| 3. 성/시를 포함하는 쿼리 | `query/`, 8,701개 회사에서 성/시를 가져오는 비율 측정, 배치 시작 전 미리보기 추가. | 이름으로 쿼리할 때 항상 성/시가 포함됩니다. API 호출 전에 잘못된 플레이스홀더가 보고됩니다. |
| 4. URL 점수 매기기 및 도메인 중복 제거 | `scoring/`. V1 점수표를 유지하고 도메인 중복 제거 및 세금 코드 거부 기능을 추가합니다. | 동일한 입력에 대해 동일한 결정이 내려집니다. 하나의 도메인에 대해 하나의 URL만 열립니다. |
| 5. AI 호출 전 컨텍스트 자르기 | `extract/slicer.py`, `extract/verifier.py`. | 뉴스 페이지의 푸터에서 연락처를 가져오지 않습니다. 연락처는 증거 단락에 있어야 합니다. |
| 6. 재시도 및 공통 리소스 | 단계 1의 `runtime/retry.py` 확장, `runtime/resources.py` 추가, 비용/속도 예산 및 남아있는 이전 재시도 코드 정리. | 402는 재시도하지 않습니다. 429는 `Retry-After`를 준수합니다. 종료 시 백오프를 중단할 수 있습니다. |
| 7. 작업 단위 분할 | `work/`. 회사당 하나의 작업에서 여러 개의 작은 작업 단위로 변경. **V1의 작업 수신 및 하트비트 메커니즘을 그대로 사용합니다.** | 실행 중 중단 후 다시 시작: 미완료 작업만 다시 실행됩니다. |
| 8. 워커 및 제어 — **다음 단계** | `runtime/worker.py`, `runtime/supervisor.py`. 속도가 정말로 충분하지 않을 때만 수행합니다. 섹션 9.3b를 참조하십시오. | 여러 워커가 중복 작업을 가져가지 않습니다. Stop 명령은 실제 프로세스를 종료합니다. |
| 9. 정책을 구성 파일로 분리 | 도메인, 티어, 점수, 쿼리 공식을 코드에서 버전이 있는 정책 파일로 이동. | 새 도메인을 추가할 때 코드 수정이 필요 없습니다. |
| 10. 지연 화면 | API 및 검토 인터페이스. | 검토가 다른 회사를 차단하지 않습니다. |
| 11. 인터페이스 통합 | 명령줄, API 및 대시보드가 모두 `service/application.py`를 호출합니다. | 세 가지 인터페이스가 동일한 결과와 동일한 제어 명령을 제공합니다. |
| 12. V1–V2 병렬 실행 | 동일한 입력 세트, 두 개의 분리된 데이터베이스. | 비용, 정확도 및 시간에 대한 보고서가 있습니다. |
| 13. 운영 전환 | V2를 주 시스템으로 선택하고 V1은 읽기 전용으로 유지합니다. | V1으로 롤백하고 체크포인트부터 계속 실행하는 지침이 있습니다. |

### 16.3 단계 1은 즉각적인 가치가 있으므로 분리

단계 1은 몇 군데만 수정하지만 V1의 비용 및 중복 데이터 문제의 대부분을 해결합니다.

따라서 단계 1을 먼저 완료하고 실제 운영에 적용한 다음 후속 단계를 진행해야 합니다.

어떤 이유로든 프로젝트를 중단해야 하는 경우에도 단계 1은 현재 V1보다 더 나은 시스템을 남길 것입니다.

이 세 항목에 대한 상세 구현 계획, 커밋 순서, 마이그레이션, 롤백 및 테스트 게이트는 `docs/v2-stage1-critical-fixes-implementation-plan.md`에 있습니다.

## 17. V2 운영 전 필수 테스트 세트

### 17.1 쿼리 및 회사 식별

1.  이름이 같고 성/시가 다른 두 회사는 서로 다른 쿼리를 생성해야 합니다.
2.  성/시 정보가 없는 이름 기반 쿼리는 **API 호출 전에 차단되어야 합니다**.
3.  성/시 정보가 없어도 세금 코드 쿼리는 여전히 실행될 수 있습니다.
4.  잘못된 플레이스홀더는 **첫 번째 쿼리가 실행되기 전에 보고되어야 합니다**.
5.  쿼리에 사용된 필드는 점수를 낮추는 데만 사용되어야 하며, URL을 자동으로 `accepted`로 만들어서는 안 됩니다.
6.  앱은 동, 도로명 또는 산업 단지를 필수 조건으로 사용하지 않습니다.
7.  퀵 서치(Quick Search)에 의해 추가된 필드는 URL을 제외하는 데 사용되어서는 안 됩니다.
8.  퀵 서치(Quick Search)가 동일한 이름의 여러 회사를 반환하는 경우, 해당 회사는 검토 대기열에 들어가야 합니다.

#### "API 호출 전 차단" 설명 (항목 2)

Firecrawl Search를 한 번 호출할 때마다 결과 사용 가능 여부와 관계없이 **비용이 발생합니다**.

잘못된 쿼리를 처리하는 두 가지 방법:

```text
잘못된 방법: 쿼리 생성 → API 호출 → 결제 → 100개의 스팸 URL 수신 → 모두 걸러내기
           → 이미 비용을 지불했지만, 아무것도 얻지 못함

올바른 방법: 쿼리 생성 → 시/도 필드가 누락된 것을 확인 → API를 호출하지 않음
           → 건너뛴 이유 기록: missing required field province
           → 비용이 들지 않음
```

"API 호출 전 차단"은 앱이 외부로 전송하기 전에 로컬에서 잘못된 쿼리를 감지해야 함을 의미합니다.

성/시 정보가 없는 회사 이름 쿼리는 다른 성/시에 있는 수많은 동명 회사를 반환할 수 있으므로 잘못된 쿼리입니다.

회사 이름만 포함된 입력의 경우는 섹션 3.8의 표에 따라 처리됩니다.

#### "배치 시작 전 보고" 설명 (항목 4)

네, 이는 **첫 번째 쿼리가 실행되기 전에** 보고해야 함을 의미합니다.

예를 들어, 사용자가 `{{province}}` 대신 `{{provine}}`을 잘못 입력하고 1,000개 회사 배치를 시작하는 경우:

```text
사전 검사 없음: 앱이 1,000개의 잘못된 쿼리를 실행 → 1,000번의 비용 발생
사전 검사 있음:    앱이 즉시 중지되고 다음과 같이 알림
                      "구성 오류: 플레이스홀더 {{provine}}이(가) 존재하지 않습니다."
                      → 비용 0원 발생
```

섹션 5.5의 미리보기는 이 검사와 동시에 실행됩니다.

### 17.1b 세금 코드

실제 세금 코드 `0100112437`는 마지막 자릿수 검사를 통과해야 한다.
전화번호 `0912345678`는 `MST` 레이블이 앞에 없을 때 세금 코드로 인식되어서는 안 된다.
식별할 수 없는 숫자 문자열은 `unknown`을 반환해야 하며, `unknown`은 URL을 제외해서는 안 된다.
`masothue` 경로의 세금 코드가 목표 세금 코드와 다른 경우 즉시 URL을 제외해야 한다.
목표와 일치하는 세금 코드는 해당 쿼리의 주요 필드로 세금 코드가 아직 사용되지 않았을 때만 점수를 얻을 수 있다.
`...-001`과 같은 13자리 형식의 세금 코드는 올바르게 인식되어야 한다.
세금 코드를 포함하는 쿼리로 찾은 페이지는 해당 세금 코드를 직접 프로모션하는 데 사용되어서는 안 된다.
동일한 `source_family`를 가진 두 도메인은 하나의 프로모션 지원 소스로만 계산되어야 한다.
거의 동일한 증거 단락을 가진 두 페이지는 하나의 소스로만 계산되어야 한다.
90% 이상 유사하지만 "PHÁT" 또는 "GROUP"과 같은 구별되는 단어가 있는 이름은 자체적으로 프로모션하기에 충분하지 않다.
동일하게 프로모션 조건을 초과하는 두 세금 코드는 `identity_ambiguous`를 생성해야 하며, 자동으로 선택해서는 안 된다.
tax-code 거부가 충분한 증거가 있는 모든 URL을 제외하는 유일한 원인인 경우, 해당 URL은 `held_for_review` 상태가 되어야 하며 회사에는 `tax_code_veto_rejects_all` 사유가 있어야 한다.
거부 전에 충분한 증거가 있는 URL이 없는 경우 `tax_code_veto_rejects_all` 메커니즘은 활성화되어서는 안 된다.

### 17.1c 데이터 보충 및 운영 상태

1.  주/도 및 세금 코드가 없는 회사는 쿼리를 생성하기 전에 Quick Search에 의해 보충되어야 한다.
2.  Quick Search에 오류가 발생하면 회사는 원래 입력 데이터로 계속 진행한다.
3.  Quick Search에서 얻은 연락처는 URL 수준이 아니라 회사 수준에 저장되어야 한다.
4.  Quick Search가 이미 출처를 제공한 URL은 다시 검색하고 스크랩해서는 안 된다.
5.  해산된 회사는 스크랩된 URL이 0개로 끝나야 한다.
6.  "등록된 주소에서 활동하지 않는" 회사는 여전히 정상적으로 실행되어야 한다.
7.  운영 상태를 읽을 수 없는 경우 회사를 차단해서는 안 된다.

1.  푸터에 있는 편집부 연락처는 회사 연락처로 저장되어서는 안 된다.

3.  연락처는 저장된 증거 단락 내에 나타나야 한다.

5.  게시 날짜가 없는 페이지는 스크랩 날짜를 자동으로 채우지 않는다.

### 17.3 재시도

#### 먼저: "HTTP 상태 코드"란 무엇인가

앱이 외부 서비스를 호출할 때마다 해당 서비스는 무슨 일이 일어났는지 알려주는 숫자를 반환한다.

첫 번째 숫자만 기억하면 된다:

| 시작 숫자 | 의미 | 누가 잘못했나 | 재시도 유용성 |
|---|---|---|---|
| **2xx** | 성공 | — | 필요 없음 |
| **4xx** | 앱 요청에 문제 발생 | 앱 측 | **아니요** — 재시도해도 동일하게 오류 발생 |
| **5xx** | 서비스 서버에 문제 발생 | 서비스 측 | **예** — 잠시 후 오류가 해결될 수 있음 |

일반 원칙: **4xx는 우리(앱)의 오류이며, 재시도는 무의미하다. 5xx는 그들(서비스)의 오류이며, 재시도하면 성공할 수 있다.**

앱이 마주치는 특정 코드:

| 코드 | 일반적인 의미 | 앱 동작 |
|---|---|---|
| `200` | 완료, 여기 데이터가 있습니다 | 계속 진행 |
| `400` | "요청이 잘못 작성되었습니다" | 재시도하지 않음. 코드 또는 구성을 수정 |
| `401` | "API 키가 잘못되었거나 만료되었습니다" | 재시도하지 않음. 사용자에게 키 확인을 알림 |
| `402` | **"잔액/크레딧이 부족합니다"** | 재시도하지 않음. 전체 배치 중단, `credit_exhausted` 기록 |
| `408` | "너무 오래 기다렸습니다, 포기합니다" | 재시도 |
| `429` | **"너무 빨리 호출했습니다, 기다려주세요"** | 그들이 말한 시간만큼 기다린 후 재시도, 동시에 동시 실행 작업 수 감소 |
| `500` | "제 서버에 오류가 발생했습니다" | 재시도 |
| `502` `503` `504` | "제 서버가 과부하 상태이거나 응답하지 않습니다" | 재시도 |
| `timeout` | 아무런 응답도 받지 못했습니다 | 재시도 |

구분해야 할 가장 중요한 두 가지 코드:

-   `402` = **잔액 부족**. 100번 재시도해도 자동으로 돈이 추가되지 않는다. 중단하고 충전해야 한다.
-   `429` = **너무 빨리 호출함**. 기다렸다가 다시 호출하면 된다. 이것은 실제 오류가 아니다.

`Retry-After`는 서비스가 429 코드와 함께 보내는 숫자로, "몇 초를 기다려야 하는지"를 알려준다. 앱은 그 숫자를 정확히 기다려야 하며, 스스로 추측해서는 안 된다.

#### 필수 테스트

1.  `503, 503, 200` 시퀀스는 정확히 세 번의 시도를 생성하고 세 번째 시도에서 성공한다.
2.  `timeout, timeout, 200` 시퀀스는 정확히 세 번의 시도를 생성하고 세 번째 시도에서 성공한다.
3.  402는 한 번도 재시도하지 않고 리소스를 `credit_exhausted` 상태로 전환한다.
4.  401은 한 번도 재시도하지 않고 API 키 오류를 보고한다.
5.  400은 한 번도 재시도하지 않는다.
6.  429는 `Retry-After`에 명시된 초를 정확히 기다리며, 스스로 추측하지 않는다.
7.  종료는 시도 간의 대기 시간을 중단할 수 있다. 워커는 60초를 모두 기다린 후에 종료될 필요가 없다.
8.  재시도는 중복 데이터 행을 추가로 생성하지 않는다.

테스트 1과 2는 가장 중요한 두 가지 테스트이다. 왜냐하면 V1은 현재 이 부분에서 오류가 있기 때문이다. V1은 두 번만 실행하고 실패를 보고한다.

### 17.4 캐시 및 다중 워커

1.  동일한 쿼리가 100번 캐시 히트해도 `search_results`에 추가 행을 생성하지 않는다.
2.  의도적으로 정확히 `(company_id, search_query, url)`을 다시 저장하려고 하면 데이터베이스에 의해 거부되어야 한다.
3.  두 워커가 동일한 결과를 저장하더라도 하나의 레코드만 허용된다.
4.  워커가 중간에 중단되면 리스가 만료된 후 작업 단위는 보류 상태로 돌아간다.
5.  재개 시 이미 완료된 작업 단위를 다시 실행하지 않는다.

### 17.4b AI 호출 1회는 URL 1개에만 해당되어야 한다

이것은 V1이 이전에 겪었던 오류이며, 재발을 방지하기 위해 테스트로 잠가야 한다.

**이전 오류:** 비용 절감을 위해 2~3개의 짧은 페이지를 **하나의** Gemini 호출로 묶는 함수가 있었다. 반환된 결과는 해당 그룹의 모든 페이지에 기록되었다. 즉, 첫 번째 URL의 전화번호가 동일 회사의 두 번째 및 세 번째 URL에도 할당되었다.

결과: 데이터베이스를 보면 세 URL 모두 연락처가 있는 것처럼 보이지만, 실제로는 하나의 URL만 가지고 있었다. 출처 추적이 잘못되었고 육안으로는 발견할 수 없었다.

**현재 상태:** 오류는 수정되었다. 현재 루프는 각 페이지를 하나씩 호출한다. 그러나 이전 그룹화 함수는 `src/ai_extractor.py`에 `_batch_short_pages`라는 이름으로 **코드에 여전히 남아 있으며**, 더 이상 호출하는 곳이 없다.

이것은 실제 함정이다. "AI 비용 절감"을 요청받은 AI 에이전트가 이 함수를 매우 쉽게 찾아 다시 연결할 수 있으며, 아무도 모르게 오류가 재발할 수 있다.

**수행해야 할 작업:**

1.  V2 코드에서 `_batch_short_pages` 함수를 삭제한다.
2.  아래 규칙을 잠그는 테스트를 추가한다.

**필수 테스트:**

1. AI 호출 1회는 정확히 하나의 `scraped_page_id`에만 해당되어야 합니다.
2. 동일 회사에 속한 세 개의 URL 중 첫 번째 URL에만 전화번호가 있는 경우: 추출 후에는 첫 번째 URL에만 연락처가 있어야 합니다. 두 번째와 세 번째 URL은 비어 있어야 합니다.
3. 저장된 모든 전화번호는 해당 전화번호를 생성한 페이지의 내용에 정확히 나타나야 합니다.
4. 어떤 함수도 여러 페이지를 하나의 AI 호출로 묶어서는 안 됩니다.
5. 퀵 서치(Quick Search)에서 얻은 회사 레벨 연락처는 URL 레벨 연락처로 저장되어서는 안 됩니다.

향후 AI 비용을 절감해야 하는 경우, 올바른 방법은 7.6항의 컨텍스트 슬라이싱(Context Slicing)입니다. 이는 여러 페이지를 병합하는 대신 각 페이지의 내용을 더 짧게 자르는 것입니다.

### 17.5 속도 및 제어

1. 정적 페이지는 `sleep(3)` 또는 `waitFor: 3000`의 영향을 받지 않습니다.
2. 셀렉터 정책(selector policy)이 있는 도메인만 대기 액션(wait action)을 받습니다.
3. 429 오류 발생 시, 정책에 따라 동시성(concurrency)이 감소합니다.
4. 드레인(Drain) 및 셧다운(shutdown)은 워커 프로세스(worker process)를 남기지 않습니다.
5. 비상 셧다운(Emergency shutdown)은 규정된 안전 대기 시간 이후에는 새로운 API 호출을 생성하지 않습니다.

## 18. V2가 V1보다 나은지 여부를 결정하기 위한 보고 지표

V1과 V2는 동일한 샘플 회사 세트에서 실행되어야 합니다.

`섀도우 런(Shadow run)`은 결과 측정을 위해 V2를 병렬로 실행하는 것이지만, 아직 V2를 주 시스템으로 사용하지 않는 것을 의미합니다.

보고해야 할 지표:

- 목표 회사에 대한 올바른 URL 비율.
- 올바른 회사 증거 섹션을 포함하는 연락처 비율.
- 제외된 푸터(footer) 또는 퍼블리셔(publisher) 연락처 수.
- 회사당 검색 호출 수.
- 회사당 스크랩 크레딧(scrape credit) 수.
- 유효한 연락처당 AI 토큰 수.
- 회사당 중간 시간.
- 가장 느리게 실행되는 상위 5% 회사 그룹의 시간.
- 중복 실행된 작업 단위(work unit) 수.
- 캐시로 인한 중복 행(row) 수.
- 완료된 작업을 다시 실행하지 않는 재개(resume) 비율.
- 셧다운(shutdown) 명령부터 워커(worker)가 없어질 때까지의 시간.

보고서 예시:

```text
100개 샘플 회사

V1:
- 760회 스크랩 호출
- 푸터에서 가져온 것으로 의심되는 18개 연락처
- 샘플 세트에서 중복된 검색 결과 행 14개
- 중앙값 시간: 회사당 92초

V2:
- 510회 스크랩 호출
- 푸터에서 가져온 것으로 의심되어 검토가 필요한 연락처 2개
- 중복된 검색 결과 행 0개
- 중앙값 시간: 회사당 61초
```

위의 수치는 단지 제시된 예시일 뿐이며, 섀도우 런(shadow run) 전에 결과에 대한 약속이 아닙니다.

V2는 다음 경우에만 V1을 대체할 수 있습니다:

- 필요한 연락처를 찾는 능력에서 V1보다 떨어지지 않을 때.
- 잘못된 회사 URL 및 잘못된 출처 연락처가 명확히 감소할 때.
- 평균 검색, 스크랩 또는 AI 토큰이 감소할 때.
- 정지/재개(Stop/resume) 및 캐시(cache)가 모든 필수 테스트를 통과할 때.

## 19. 1차 개발에서 아직 수행되지 않은 내용

1차 개발에서는 사용자가 기존 Gemini와 OpenRouter 무료 모델 중에서 선택할 수 있도록 하는 기능이 구축되지 않았습니다.

V2는 향후 전체 파이프라인을 수정하지 않고도 공급자(provider) 선택을 추가할 수 있도록 하나의 공통 AI 호출 게이트웨이만 생성합니다.

1차 개발에서는 전화번호를 wrong, invalid 또는 same으로 자동으로 분류하지 않습니다.

앱은 사용자가 제공한 레이블(label)을 읽고, 번호를 표준화하여 비교만 합니다.

### V1에서 재사용되는 테스트 도구

V1에는 `리플레이 모드(replay mode)`가 있습니다. 이는 저장된 데이터에 대해 전체 흐름을 다시 실행하지만 비용이 드는 API를 호출하지 않습니다.

V2는 이 모드를 17항의 전체 테스트 세트와 18항의 병렬 실행 단계에 대한 주요 테스트 도구로 사용합니다.

덕분에 V2 테스트의 대부분은 API 비용을 발생시키지 않습니다.

V1의 `강제 새로고침(Force refresh)`도 유지되며, 특정 회사에 대한 새로운 데이터를 다시 가져와야 할 때 사용됩니다.

## 20. 디버깅을 위한 실시간 로그 테이블

목표: 회사가 잘못된 결과를 생성할 때, 사용자는 **코드를 읽을 필요 없이** 원인을 찾아야 합니다.

### 20.1 V1 로그의 문제점

V1은 `pipeline_logs` 테이블과 날짜별 JSONL 파일에 로그를 기록합니다. 이 로그는 “무엇이 실행되었는지”는 기록하지만, “앱이 왜 그렇게 결정했는지”는 부족하게 기록합니다.

올바른 URL이 제외될 때, 현재 로그는 어떤 단계에서 어떤 이유로 제외되었는지 알려주지 않습니다.

### 20.2 V2의 로그 테이블

V2는 한 테이블을 추가하며, 각 행은 **하나의 결정**입니다:

| 열 | 내용 | 예시 |
|---|---|---|
| `time` | 베트남 시간 기준 시점 | `2026-07-28 14:32:07` |
| `company_id` | 어떤 회사 | `4821` |
| `work_unit_id` | 어떤 작은 작업 | `wu_4821_scrape_7` |
| `module` | 어떤 파일이 결정을 내렸는지 | `scoring/domain_dedupe.py` |
| `action` | 무엇을 하고 있는지 | `dedupe_domain` |
| `decision` | 결과 | `rejected` |
| `reason` | **이유** | `duplicate_domain: yellowpages.vn 점수 62가 이미 존재함` |
| `target` | 영향을 받는 대상 | `https://yellowpages.vn/minh-an/branch` |
| `cost` | 이 단계의 비용 | `0` |
| `duration_ms` | 소요 시간 | `4` |

`reason` 열은 가장 중요한 열입니다. **`rejected`, `skipped`, `deferred` 또는 `cancelled`의 모든 결정에는 `reason`이 필수적으로 포함되어야 합니다.**

### 20.3 디버깅 시 사용 방법

사용자는 로그 화면을 열고, 하나의 `company_id`로 필터링한 다음 위에서 아래로 읽습니다.

예시: Minh An 회사가 연락처를 생성하지 않는 경우:

```text
14:32:01  identity/enricher      quick_search    성공    tax_code=3701234567 (미확인)
14:32:03  query/planner          plan_query      생성됨    "MINH AN" "Bình Dương" (연락처)
14:32:05  search/cache           cache_lookup    적중        검색 크레딧 1개 절약
14:32:06  scoring/scorer         score_url       62         yellowpages.vn/minh-an
14:32:06  scoring/domain_dedupe  dedupe_domain   거부됨   중복 도메인: 이미 62점 있음
14:32:07  identity/status_gate   status_check    비활성   "해산됨" → 회사 중단
```

읽고 나면 즉시 알 수 있습니다: 회사가 해산되었기 때문에 연락처가 생성되지 않은 것이지, 앱 오류 때문이 아닙니다.

### 20.4 세 가지 필수 사항

1.  **실행 중 실시간으로 확인.** V1의 `/ws/logs` 경로를 재사용하여 새로운 행을 대시보드에 푸시하고, 새로고침 버튼을 누를 필요가 없습니다.
2.  **`company_id` 및 `work_unit_id`로 필터링 가능.** 이 두 열에는 인덱스(index)가 있어야 합니다. 그렇지 않으면 테이블이 커질 때 화면이 느려질 것입니다.
3.  **테이블 자동 정리.** 이 테이블은 매우 빠르게 커집니다. 상세 로그는 30일만 유지되며, 그 후 삭제됩니다. 집계된 데이터는 삭제 전에 별도의 테이블로 누적됩니다.

자동으로 정리하지 않으면 몇 달 후 로그 테이블이 실제 데이터보다 커지고 전체 시스템을 느리게 만들 것입니다.

## 21. AI 에이전트를 위한 아키텍처 기록

이 항목은 실제 상황에 대비합니다: 대부분의 코드는 AI 에이전트가 작성할 것이며, 에이전트가 매번 전체 코드베이스를 다시 읽어야 한다면 느리고 토큰을 많이 소모하며 오해하기 쉽습니다.

### 21.1 네 가지 필수 파일

| 파일 | 용도 | 누가 읽는가 |
|---|---|---|
| `AGENTS.md` (루트 디렉터리) | 필수 규칙 및 안내 테이블 | AI 에이전트가 자동으로 가장 먼저 읽음 |
| `docs/architecture/INDEX.md` | "X를 수정하려면 어떤 파일을 읽어야 하는가" 테이블 | AI 에이전트, 작업을 할당받을 때 |
| `docs/architecture/<module>.md` | 모듈의 계약 | AI 에이전트, 해당 모듈을 수정할 때 |
| `docs/implementation/STATUS.md` | 구현 상태, 검증 증거 및 다음 단계 | 모든 에이전트, 세션을 시작할 때와 종료하기 전 |

`AGENTS.md`는 Codex 및 여러 AI 도구가 작업을 시작하기 전에 자동으로 읽는 파일 이름입니다. 이 이름을 올바르게 지정하면 에이전트에게 매번 상기시킬 필요가 없습니다.

`AGENTS.md`는 안정적인 규칙만 유지합니다. 세션별 변경 진행 상황을 이 파일에 기록하지 않습니다. 진행 상황은 `STATUS.md`에 있어 에이전트가 임시 메모를 장기적인 지시로 오해하지 않도록 합니다.

`AGENTS.md`에는 고정된 지시사항이 있어야 합니다: **시작하기 전에 `docs/implementation/STATUS.md`를 읽고 확인하십시오; 구현 세션을 종료하거나 인수인계하기 전에 해당 파일을 업데이트하십시오.**

부트스트랩 세트가 존재하지 않거나 일부 누락된 경우, `AGENTS.md`는 에이전트에게 **첫 번째 코드 수정 전에** §21.6의 프로토콜에 따라 자체적으로 생성하도록 요청해야 합니다. 읽기/평가 작업은 임의로 파일을 생성하지 않으며, 에이전트는 부트스트랩이 누락되었음을 보고만 합니다.

### 21.2 안내 테이블

이 부분은 토큰을 가장 많이 절약합니다. 에이전트가 `src/` 전체를 읽게 하는 대신, 이 테이블은 수정해야 할 파일을 직접 가리킵니다.

`docs/architecture/INDEX.md` 내용 예시:

```text
| 수정 사항                       | 관련 파일                       | 관련 테스트                 |
|---------------------------------|---------------------------------|-----------------------------|
| 세금 코드 식별 방법             | src/v2/identity/taxcode.py      | tests/test_taxcode.py       |
| 도메인 점수                     | policy/sources.yaml             | tests/test_scorer.py        |
| 쿼리 공식                       | policy/queries.yaml             | tests/test_query.py         |
| 도메인당 1개의 URL만 유지       | src/v2/scoring/domain_dedupe.py | tests/test_dedupe.py        |
| AI 호출 전 콘텐츠 자르기        | src/v2/extract/slicer.py        | tests/test_slicer.py        |
| API 오류 시 재시도 규칙         | src/v2/runtime/retry.py         | tests/test_retry.py         |
```

에이전트 규칙: **`INDEX.md`를 먼저 읽고, 지정된 파일만 열며, 전체 디렉터리를 스캔하지 마십시오.**

### 21.3 모듈의 계약

각 모듈은 최대 한 페이지 분량의 짧은 설명 파일을 가집니다:

```text
# scoring/domain_dedupe.py

임무: 점수가 매겨진 URL 목록에서, 각 도메인별로 가장 높은 점수의 URL만 유지합니다.

입력: URL 목록, 각 URL은 다음을 포함합니다: url, domain, score
출력: URL 목록, 각 URL은 다음을 추가로 포함합니다: keep (참/거짓), reason

금지 사항: API 호출, 데이터베이스 쓰기, 전역 설정 읽기.

불변 규칙:
- 제외된 URL은 여전히 반환되어야 하며 reason = "duplicate_domain"이 함께 제공되어야 합니다.
- 점수가 같으면 source_priority가 더 높은 URL을 유지합니다.

테스트: tests/test_dedupe.py
```

"입력 / 출력 / 금지" 세 줄은 가장 중요한 부분입니다. 이는 에이전트에게 주변 코드를 읽을 필요 없이 모듈의 한계를 알려줍니다.

### 21.4 업데이트 규칙

- 코드를 수정하여 문서의 한 줄이 틀리게 되면 **동일한 변경에서 문서를 수정해야 합니다.**
- 문서는 계약 및 규칙만 기록합니다. 코드를 문서에 복사하지 마십시오.
- 문서와 코드가 다를 경우, 이는 미완성된 오류입니다. 어느 쪽이 맞는지 묵묵히 가정해서는 안 됩니다.

두 가지 질문을 구분하십시오:

| 질문 | 결정 소스 |
|---|---|
| 현재 앱이 실제로 무엇을 하는가? | 실행 가능한 코드, 마이그레이션 및 테스트 |
| 비즈니스 요구사항에 따라 앱이 무엇을 해야 하는가? | 베트남어 계획 및 사용자 승인 결정 |
| 모듈이 어떤 인터페이스를 약속했는가? | 모듈 계약 및 테스트 |
| 이 변경 사항이 능동적으로 결정되었는가? | 변경 로그, ADR 또는 승인된 이슈 |

예시: 계획에는 `unconfirmed` 필드가 거부되어서는 안 된다고 명시되어 있지만, 코드는 거부를 허용합니다. 코드는 현재 동작을 정확하게 설명하지만, 그 동작은 버그입니다; 코드를 수정하고 회귀 테스트를 추가해야 하며, 버그를 합법화하기 위해 계획을 수정해서는 안 됩니다.

#### 완료의 정의

다음 관련 항목들이 동일한 변경 내에서 업데이트될 때까지는 변경이 완료되지 않습니다:

| 변경 사항 | 필수 문서/테스트 |
|---|---|
| `src/v2/<area>/<module>.py` | `docs/architecture/` 내 해당 모듈 계약 및 관련 테스트 |
| `src/v2/` 내 새 파일 | `docs/architecture/INDEX.md`에 줄 추가 |
| 정책 키 | `docs/architecture/policy.md` 및 정책 테스트 |
| 테이블, 컬럼 또는 인덱스 | `docs/architecture/schema.md`, 마이그레이션 및 테스트 |
| 비즈니스 규칙 또는 수치 임계값 | 두 계획 모두, §24 변경 로그 및 회귀 테스트 |
| 구현 세션 종료 또는 인수인계 | `docs/implementation/STATUS.md`에 검증 증거 및 다음 단계 포함 |

리포지토리는 `scripts/check-doc-sync.sh`와 같은 검사 스크립트를 유지하고, 프리커밋과 CI에서 동일한 스크립트를 실행해야 합니다. 최소한의 게이트는 V2 코드가 변경되었지만 관련 아키텍처 문서가 변경되지 않은 경우를 차단해야 합니다. 훅은 문서 누락을 방지할 뿐이며, 테스트와 리뷰는 내용이 올바른지 여전히 확인해야 합니다.

`.git/hooks/pre-commit`에만 유일한 검사 로직을 두지 마십시오. `.git/hooks` 디렉터리는 커밋되지 않으며 다른 머신에서 자동으로 인식되지 않습니다.

#### Graphify 사용 시

`INDEX.md`와 모듈 계약은 각 작업에서 읽힙니다. Graphify는 `INDEX.md`가 충분하지 않을 때, 대규모 온보딩/리팩터링 시 또는 마일스톤 종료 시에만 사용됩니다; 작은 변경 후에 매번 다시 빌드하지 않습니다.

그래프를 생성하거나 읽는 모든 작업은 `src/`, `dashboard/`, `scripts/`, `tests/`와 같은 프로젝트 코드와 `graphify/`, `version1-lasted/`, 종속성/벤더를 제외한 유형으로 제한되어야 합니다. 필터링하지 않으면 에이전트가 V2 대신 도구의 아키텍처나 V1 코드를 잘못 학습할 수 있습니다.

### 21.5 두 계획 버전은 일치해야 합니다

이 계획에는 두 가지 버전이 있습니다:

| 버전 | 파일 | 대상 |
|---|---|---|
| 베트남어 | `docs/v2-modular-refactor-plan.md` | 독자, 관리자 |
| 영어 | `docs/v2-modular-refactor-plan.en.md` | AI 에이전트 |

영어 버전은 문장별 번역본이 아닙니다. 이는 동일한 섹션 번호와 숫자를 사용하는 더 짧은 사양서입니다.

두 버전을 일치시키는 규칙:

항목 번호 체계를 동일하게 유지합니다. 베트남어 버전의 3.7항은 영어 버전의 3.7항과 동일합니다.
비즈니스 결정이 변경되면 **두 버전 모두 동시에 수정해야 합니다**.
모든 숫자는 한 곳에만 작성하고 다른 버전에는 그대로 반복해야 합니다. 예: 35점 임계값, 10개 URL, 25% 점수 감소.
두 버전이 다를 경우 **베트남어 버전이 정확합니다**. 이는 사용자가 결정한 버전이기 때문입니다.
각 버전의 끝에는 날짜와 수정된 항목을 기록하는 변경 이력 테이블이 있습니다.

### 21.6 AI 에이전트와 채팅 세션 간의 진행 상황 핸드오버

목표: 새로운 에이전트 또는 채팅 세션이 어떤 작업이 수행되었는지 추측할 필요 없이 즉시 작업을 계속할 수 있도록 하는 것입니다. 단, 문서를 신뢰하기 전에 실제 상태를 확인해야 합니다.

#### 문서 세트가 존재하지 않을 때의 자체 부트스트랩

코드 추가/수정/삭제가 허용되는 모든 작업에 대해, 에이전트는 첫 번째 코드 편집 전에 다음 경로를 확인해야 합니다:

```text
AGENTS.md
docs/architecture/INDEX.md
docs/implementation/STATUS.md
docs/implementation/work-items/
scripts/check-doc-sync.sh
```

누락된 부분이 있다면, 에이전트는 저장소 범위 내에서 누락된 부분을 자체적으로 생성합니다. 부트스트랩이 없다는 이유만으로 멈춰서 질문하지 않습니다. 규칙:

1.  기존 파일을 덮어쓰지 않습니다. 기존 내용을 읽고 유지하며, 누락된 필수 섹션만 추가합니다.
2.  정확한 경로로 디렉터리를 생성합니다. V1, 백업, Graphify 또는 다른 저장소에서 문서를 스캔하거나 복사하지 않습니다.
3.  베트남어 V2 계획을 비즈니스 소스로 사용합니다. 증거가 없는 모듈, 상태 또는 결정을 자체적으로 발명하지 않습니다.
4.  초기 `INDEX.md`는 코드와 테스트로 확인된 파일만 나열합니다. 확인되지 않은 항목은 `unverified`로 기록하고 추측하지 않습니다.
5.  현재 작업이 영향을 미치는 모듈을 수정하기 전에 해당 모듈에 대한 모듈 계약을 생성합니다. 전체 코드베이스에 대해 대량의 빈 계약을 생성할 필요는 없습니다.
6.  초기 `STATUS.md`는 `git status`, 기존 코드/마이그레이션 및 실제로 실행된 테스트를 기반으로 작성됩니다. 계획에 따라 `completed`로 기록하지 않습니다.
7.  현재 작업에 대한 작업 항목 파일을 소유자, 파일 범위, 승인 기준, 상태 및 증거와 함께 생성합니다.
8.  초기 `scripts/check-doc-sync.sh`는 읽기 전용으로 실행되어야 합니다. 파일을 자체적으로 수정하거나, API를 호출하거나, 관련 계약/STATUS가 없는 V2 코드 변경을 차단하지 않습니다.
9.  `STATUS.md`에 이벤트를 기록합니다: `bootstrap_created` 또는 `bootstrap_repaired`, 타임스탬프, 생성/추가된 파일 및 확인 명령.
10. 코드 편집 전에 부트스트랩 검사를 실행합니다:

    ```text
   모든 필수 경로가 존재해야 합니다.
   STATUS에 Current handoff 및 Verification이 있습니다.
   현재 작업 항목에 소유자 및 승인 기준이 있습니다.
   doc-sync 검사기가 실행될 수 있습니다.
   
```

작업이 코드 수정 없이 읽기, 설명, 검토 또는 진단만 요구하는 경우, 에이전트는 자체적으로 부트스트랩을 생성하지 않습니다. 에이전트는 부트스트랩이 누락되었음을 간략하게 보고하고, 사용자가 저장소 변경을 허용할 때만 생성합니다.

권한 또는 충돌하는 상태로 인해 부트스트랩 생성이 실패하면, 에이전트는 코드 수정을 계속할 수 없습니다. 가능하면 블로커를 기록하고 사용자에게 처리를 요청합니다.

#### 배포 상태 파일

`docs/implementation/STATUS.md`는 현재 진행 상황을 요약한 것입니다. 이 파일은 간결해야 하며, 다음 단계를 수행하는 데 도움이 되는 정보를 우선시해야 하며, 필수 구조를 가져야 합니다:

```markdown
# V2 Implementation Status

Last updated: 2026-07-29 16:30 +07
Updated by: <에이전트 또는 업데이트 담당자>
Current milestone: <§16의 현재 단계>
Overall state: pending | in_progress | blocked | completed

## Current handoff
Next action: <즉시 시작할 수 있는 구체적인 작업 하나>
Read first: <먼저 읽어야 할 계획 섹션, 모듈 계약, 코드 및 테스트>
Do not redo: <완료되었으며 증거가 있는 작업>

## Stage progress
| Stage/work item | Status | Evidence |

## Work completed this session
<변경된 동작 및 파일 목록>

## Verification
<실행한 명령, 결과, 실패 중이거나 실행하지 않은 테스트>

## Decisions made
<새로운 결정 및 관련 계획/ADR/이슈 링크>

## Blockers and open questions
<차단 요소, 담당자, 계속 진행하기 위한 조건>

## Working-tree warning
<현재 작업 범위 밖의 변경 사항. 수정하거나 되돌리지 말 것>
```

`Next action`은 실행 가능한 작업이어야 합니다. 예: “`tests/test_taxcode.py`에 실패하는 테스트 7번 작성”. “2단계 계속”과 같이 모호하게 기록하지 않습니다.

#### 세션 시작 시 프로토콜

1.  `AGENTS.md`를 읽습니다.
2.  작업에 코드 수정이 포함된 경우, 자체 부트스트랩 검사를 실행하고 위 항목에 따라 누락된 부분을 생성/수정합니다.
3.  `docs/implementation/STATUS.md`를 읽습니다.
4.  `git status`, 관련 파일/마이그레이션 및 적절한 테스트를 통해 실제 상태를 확인합니다.
5.  `STATUS.md`가 실제 상태와 다를 경우, 차이점을 명확히 기록하고, `STATUS.md`를 신뢰하기 전에 수정합니다.
6.  `Next action`부터 시작합니다. 반대되는 증거가 없는 한 `Do not redo` 부분을 다시 수행하지 않습니다.

#### 작업 중 및 종료 전 프로토콜

모든 코드 라인 후에 `STATUS.md`를 수정할 필요는 없습니다. 의미 있는 체크포인트에서 업데이트해야 합니다:

-   작업 항목 또는 단계의 상태가 변경될 때.
-   테스트 그룹이 실패에서 통과로 전환되거나 새로운 실패가 발생할 때.
-   새로운 설계/비즈니스 결정이 있을 때.
-   블로커가 있을 때.
-   다른 에이전트에게 작업을 인계하거나 채팅 세션을 종료할 때.

종료 또는 핸드오버 전에 에이전트는 다음을 기록해야 합니다:

1.  완료된 작업과 변경된 파일.
2.  실행된 확인 명령과 정확한 결과; 아직 실행되지 않았다면 `not run`으로 기록해야 합니다.
3.  여전히 실패하는 테스트, 블로커 및 미해결 질문.
4.  구체적인 `Next action`.
5.  다음 에이전트가 읽어야 할 파일/문서 항목 목록.
6.  사용자 또는 다른 작업에 속하며 유지되어야 하는 작업 트리 변경 사항.

코드를 수정했다는 이유만으로 `completed`로 기록해서는 안 됩니다. 관련 승인 기준이 충족되고 증거가 있을 때만 `completed`로 기록합니다. 세션이 중간에 중단된 경우, 수행된 부분을 `in_progress`로 기록하고 결과를 추측하지 않습니다.

#### 여러 에이전트가 병렬로 실행될 때

여러 에이전트가 `STATUS.md`의 한 부분을 자유롭게 동시에 수정하지 않습니다. 사용:

```text
docs/implementation/STATUS.md
docs/implementation/work-items/<work-item-id>.md
```

각 작업 항목은 한 번에 정확히 한 명의 소유자를 가지며, 명확한 파일 범위, 승인 기준, 증거 및 상태를 가집니다:

```text
대기 중 → 진행 중 → 완료됨
                    ↘ 차단됨
```

에이전트는 자신이 소유한 작업 항목 파일만 수정합니다. `STATUS.md`는 작업 항목을 요약하고 연결합니다. 조정자/에이전트는 충돌을 피하기 위해 요약 부분을 업데이트합니다.

#### 오래되거나 잘못된 상태 방지 규칙

`STATUS.md`는 핸드오버 지침이며 최종 증거가 아닙니다. 새 에이전트는 코드, Git 및 테스트를 통해 중요한 주장을 확인해야 합니다. 파일에 "test pass"라고 기록되어 있지만 명령/결과가 없거나 현재 코드가 해당 타임스탬프 이후 변경된 경우, 해당 주장은 확인되지 않은 것으로 간주합니다.

## 22. 각 단계의 필요 수준 및 소요 시간

이 섹션은 사용자가 기본적인 IT 지식을 가지고 AI 에이전트를 사용하여 코드를 작성하고 결과를 수동으로 확인하는 상황을 위한 것입니다.

따라서 시간은 두 가지 다른 부분으로 나뉩니다.

- **AI 코드 작성 시간**: 에이전트와의 작업 세션 수로 계산됩니다.
- **사용자 확인 시간**: 사용자가 결과가 올바른지 확인하는 데 실제로 소요되는 시간입니다.

이 방식으로는 **코드 작성보다 확인에 더 많은 시간이 소요됩니다**.

### 22.1 세 가지 필요 수준

| 수준 | 의미 |
|---|---|
| **필수** | 수행하지 않으면 V2가 V1보다 나아지지 않거나 잘못된 데이터가 생성됩니다. |
| **권장** | 비용을 절감하거나 오류를 현저히 줄이지만, 연기될 수 있습니다. |
| **다음 단계** | 첫 단계에서는 완전히 생략할 수 있습니다. |

### 22.2 평가표

| 작업 | 수준 | 이유 | AI 코드 작성 | 확인자 |
|---|---|---|---|---|
| `waitFor: 3000` 및 `DELAY_SECONDS` 제거 | **필수** | 각 회사당 약 60초 절약, 2줄 수정 | 1 세션 | 1 시간 |
| 캐시 히트 버그 수정 + 89,070개 중복 행 정리 + 고유 키 추가 | **필수** | 중복 데이터가 점차 증가하고 있음 | 1 세션 | 3 시간 |
| 재시도 수정: `max_attempts`, 4xx/5xx 분류 | **필수** | 너무 일찍 포기하여 결과 손실 발생 중 | 1–2 세션 | 3 시간 |
| 세금 코드 확인 모듈 (체크섬, 3가지 결과) | **필수** | 잘못된 회사 데이터 차단. 오프라인 테스트 가능, API 비용 없음 | 1 세션 | 2 시간 |

| 도메인 중복 제거: 도메인당 1개 URL | **필수** | 동일한 페이지를 10번 구매하는 것 방지 | 1 세션 | 3 시간 |
| `reason` 컬럼이 있는 직접 로그 테이블 | **필수** | 없으면 모든 후속 확인 단계가 매우 느려짐 | 1–2 세션 | 2 시간 |

| 도메인, 점수, 쿼리를 정책 파일로 이동 | **권장** | 나중에 비즈니스 로직 변경 시 코드 수정 불필요 | 2 세션 | 4 시간 |

### 22.3 총 시간

| 그룹 | AI 코드 작성 | 확인자 | 실제 예상 |
|---|---|---|---|
| **필수** | 12–15 세션 | 약 28 시간 | **2~3주** |
| **권장** | 8–10 세션 | 약 23 시간 | 추가 2~3주 |
| **다음 단계** | 12 세션 | 약 27 시간 | 추가 3~4주 |

실제 예상은 하루 약 2~3시간 작업 기준입니다.

"실제 예상" 수치는 왼쪽 두 열의 합계보다 큰데, 실제로는 AI가 잘못 수행한 부분 수정, 실제 배치 실행 대기, 결과 판독 등의 추가 작업이 발생하기 때문입니다.

### 22.4 시간이 부족할 때 권장되는 작업 순서

약 2주 정도 남았다면, 다음 네 가지 그룹을 순서대로 수행하십시오.

```text
1일차        AGENTS.md + INDEX.md + 모듈 계약 + STATUS.md
              → 이후 모든 AI 세션이 더 저렴해지도록 먼저 수행

2일차        이유 열이 있는 로그 테이블
              → 이후 단계를 훨씬 더 빠르게 확인할 수 있도록 일찍 수행

3-5일차      세 가지 저렴한 오류: waitFor, 캐시 히트 + 고유 키, 재시도
              → 이는 투입 시간당 가장 명확한 결과를 제공하는 부분입니다.

6-10일차     현재 V1의 네 가지 동작: 빠른 검색, 상태 게이트,
              도메인 중복 제거, 세금 코드 체크섬
              → 이 부분은 정확성과 비용을 보호합니다.
```

처음 두 가지 작업은 눈에 보이는 결과를 생성하지 않지만, 먼저 수행하면 모든 후속 작업이 단축됩니다. 나중에 수행하면 매번 확인할 때마다 코드를 찾아야 합니다.

계획의 나머지 부분은 다음 단계를 위해 남겨두며, V2 실행 가능성에는 영향을 미치지 않습니다.
